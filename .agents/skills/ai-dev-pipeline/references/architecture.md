# 架構原則與分層

## 原則：跨平台高可用，非必要絕對不耦合
- **跨平台優先**：核心邏輯不依賴任何平台；OS、檔案系統、路徑、行程、外部 CLI、資料庫、雲端服務都經 Port 存取，各平台各自實作 Adapter。
- **高可用**：外部依賴失效時可降級或替換；設計逾時、重試、容錯與狀態可恢復。
- **非必要不耦合**：模組只透過契約溝通，不共用內部狀態、不引用對方實作。耦合要寫明必要理由，寫不出就拆。
- 每個模組可獨立測試、獨立替換。

## 何時引入 Port
**依專案的製作順序**（見 [project.md](project.md)）。專案沒規定時：先做能跑的原型（UI 殼＋核心資料流、假資料），驗證可行後再抽 Port／Adapter；但從第一天起就**不在核心寫死平台 API 或路徑**，平台呼叫集中在一處，方便之後抽出。

## 架構選型
| 架構 | 優勢 | 代價 | 適用 |
|---|---|---|---|
| 傳統三層 | 簡單、快 | 業務與資料庫耦合 | 簡單 CRUD，無跨平台需求 |
| 洋蔥 | 領域核心純粹 | 介面與 DTO 轉換多 | 業務複雜、生命週期長 |
| 六角形／Ports & Adapters | 易換外部元件、易插 Mock | 較抽象 | 多入口、多儲存、跨平台 |
| CQRS | 讀寫各自最佳化 | 最終一致性延遲 | 讀寫比例懸殊、寫入極複雜 |

- **預設六角形＋洋蔥**：領域層最內，核心經輸入埠被呼叫、經輸出埠呼叫外部，Adapter 最外。
- 三層只在簡單 CRUD 時用並寫理由；業務規則仍不得直接寫 SQL 或依賴 ORM 型別。
- CQRS 只在有明確讀寫效能差異時加，並寫一致性策略。
- 架構文件寫出：選了什麼、為什麼、捨棄什麼、何時升級。

## 分層與職責
| 層 | 職責 | 不可做 |
|---|---|---|
| 渲染層 | 把結構化資料畫出來 | 業務邏輯、直接碰應用層或資料庫 |
| 介面／API 層（輸入 Adapter） | 路由、驗證身分、參數校驗、DTO 轉換、全域錯誤轉換 | 商業規則 |
| 命令層（應用層的一部分） | 把改變狀態的意圖封成 Command | — |
| 應用層（Use Case） | 編排流程、管交易、經 Port 協調 | 計算規則 |
| 領域層 | 純商業規則（Entity、Value Object、Domain Service、Domain Error） | 引用框架、資料庫、UI、平台 |
| 基礎設施 Adapter | 實作內層定義的 Port | 被內層直接引用 |

- 依賴只能由外往內：渲染 → API → 命令 → 應用 → 領域；Adapter 實作內層定義的 Port（依賴反轉）。
- 不跳層；層間只傳 DTO／Command／領域物件，不外漏內部型別（例如 ORM 實體不回 API）。
- 每個主要 Use Case 畫一條跨層資料流；附依賴圖標出層級與每個必要耦合的理由。

## 標準資料流（例：提交訂單）
渲染層收集輸入 → API 層驗權限與參數 → 打包 `SubmitOrderCommand` → 應用層開交易、經 Port 讀資料 → 領域層算規則 → 應用層經 Port 儲存 → API 回結果 → 渲染層更新。

## 審查時檢查
寫死平台路徑／指令／API；繞過 Port 引用他模組實作；無理由耦合；依賴方向錯；領域層引用框架；渲染或 API 層藏商業規則；跳層；內部型別外漏。
