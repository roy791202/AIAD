# 演算法與效能：先量測，再用數學推理選解法

## 預製期
- 為關鍵操作訂可量測的**效能預算**（例：UI 互動 < 100 ms、啟動 < 2 s、處理 10 萬筆 < 1 s、記憶體上限），寫進工單驗收條件。
- 有預算的操作，TDD 封包要含 benchmark（Rust criterion、TS Vitest bench 或計時測試），以代表性資料規模量測；超出預算或比基準退步超過約定比例（例如 20%）就失敗。

## 實作期
1. **先量測**：用 `cargo bench`／criterion、`cargo flamegraph`、DevTools Performance 找出真正瓶頸，記下基準。沒有數據不優化。
2. **推導複雜度**：寫出現況與新解法的時間／空間 Big-O 與一兩行推導（例：「外層 n × 內層線性搜尋 n = O(n²)；改 HashMap O(1) 均攤 → O(n)」），說明 n 的實際規模與常數因子。
3. **選對工具**：雜湊、排序＋二分、雙指標、滑動視窗、前綴和、DP、貪婪（要能證明貪婪選擇性質）、BFS/DFS/Dijkstra、堆積、Trie、並查集、分治、memoization、串流與增量計算、位元運算。平行化只在量測證明 CPU 是瓶頸且資料可切分時用。
4. **證明正確**：寫出迴圈不變量、終止條件、邊界（空、單一、重複、溢位、極大 n），用單元或性質測試涵蓋。
5. **簡單優先**：n 小或不在熱點時選最易讀的；換複雜演算法要在註解寫理由與複雜度。
6. **記錄前後數字**：回報附 benchmark（中位數、樣本數、機器環境）。

## 硬規則
- 由外部決定大小的輸入在熱點路徑上不得有 O(n²) 以上，除非已設硬上限並說明；遞迴要有深度上限。

## 審查時
熱點與外部輸入處有複雜度推導；無意外 O(n²)（迴圈內線性搜尋、重複排序、字串反覆串接）；效能宣稱有前後數字；不變量與邊界論證成立；無缺乏量測依據的複雜優化。驗證者要跑效能回歸並對照預算。
