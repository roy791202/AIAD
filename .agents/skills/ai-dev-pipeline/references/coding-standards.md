# 程式寫法標準（實作者寫、審查者查）

## SOLID，但不過度設計
- **S** 一個類別／函式只有一個改變理由。**O** 新行為優先擴充，不改穩定程式。**L** Adapter 必須能完全替換其介面。**I** 介面小而專一。**D** 高層與領域依賴 Port，不依賴具體實作。
- 只為工單與 BDD 實際需要的情境寫抽象；只有一種實作就不做工廠、策略或泛型框架；三次重複才抽共用。
- SOLID 與「簡單」衝突時，以工單範圍和可測試性為準；拿不定選較簡單的，回報裡寫一句理由。

## Clean Code
1. **命名名副其實**：揭示意圖（`elapsed_days` 不是 `d`）、不誤導、可搜尋；除極短迴圈計數器外不用 `e`、`data`、`tmp`。
2. **函式短小專一**：盡量 20 行內（上限 30），參數 0–2 個，3 個以上封成物件／DTO。
3. **用程式表達而非註解**：只留版權、解釋「為什麼」、後果警告；刪廢話註解與註解掉的舊程式。
4. **錯誤處理不破壞邏輯**：不回傳錯誤碼；用明確錯誤型別（Rust `Result<T, 專屬 enum>` 與 `?`，產品程式不用 `unwrap()`／`panic!` 處理可預期錯誤；TS 用自訂 Error）。錯誤在 API 層統一轉成對外格式。
5. **不傳入也不回傳 null**：沒資料回空集合；可能不存在用 `Option`／`T | undefined`。
6. **童子軍法則**：只限本卡允許的檔案、只在本來就在改的程式附近，不改行為；範圍外問題寫進回報由高階開新卡。

## 落實架構的寫法
1. **衛句**：不合法條件開頭就 return／回錯誤，不層層巢狀。
2. **依賴注入**：服務經建構函式接收 Port（Rust trait、TS interface），只在 composition root 組裝；測試注入假實作。
3. **充血模型**：領域物件自己管狀態與規則（`member.deduct_points(n)`），不讓 Service 任意改；單純 DTO／設定物件不必硬加行為。
4. **宣告式**：資料轉換優先 iterator／stream 鏈；鏈太長、副作用複雜或熱路徑時可用清楚的迴圈。
5. **消除魔法數字**：用 enum、具名常數與行為命名的方法。

## 提交前自我審查清單
- [ ] 本卡範圍內無 TODO 樁、半成品或被 skip 的測試；本卡 TDD 全 Green。
- [ ] 函式 ≤20 行（最多 30）、參數 ≤3、if/for 縮排 ≤2 層。
- [ ] 命名見名知意；無魔法數字、廢話註解、註解掉的程式。
- [ ] 無錯誤碼、無 null、產品程式無 `unwrap()`／`panic!` 處理可預期錯誤。
- [ ] 無不經意的全域／外部狀態修改；副作用集中在 Adapter。
- [ ] 無在方法內自行 new 依賴；領域物件不是貧血模型。
- [ ] 無 print／console.log 當日誌、無拼接 SQL 或 shell、無寫死金鑰、無內部錯誤外洩（見 [readiness.md](readiness.md)）。
- [ ] linter（`cargo clippy`、ESLint 等）無新增警告。
- [ ] 熱點路徑寫了複雜度推導；效能修改附前後數字（見 [performance.md](performance.md)）。

## 審查時
明顯違反就退回；小問題列為建議不擋 PR。以「童子軍法則」為名越界或改變行為一律退回。
