F1：可量測回應性預設

既有需求是快照寫入不阻塞 UI。以下數字為建議驗收 profile，尚未成為產品 SLA。

  • 30 秒內30次普通選取操作；至少3次輸入在已證實的寫入區間內。
  • 端到端保守上界延遲：p95 ≤250ms，最大值 ≤1000ms；兩者包含等號。
  • nearest-rank p95；整數 monotonic microseconds；事件／frame 時間校準不確定度 ≤20ms。
  • 沒有可證明寫入區間、重疊不足或錄影失真時為 BLOCKED_OBSERVATION；不擅自增加 sleep／fault hook 或宣稱產品失敗。

選取兩個既有 fixture 物件 A/B，確認各輸入對應的高亮／身份回應；選取本身不算內容變更。未提供 M07 核准觀察 seam 時，原生執行等待其架構提案，不能由 M08 私加接口。

F2：精確 validator 契約與 fixture

提議 H1 只做純資料檢查；輸出只有 SCHEMA_VALID／REJECTED 及精確 issue，證據等級固定 SCHEMA_UNIT。它不回傳 native PASS，也不驗證虛構檔案／PID實際存在。所有示例的 record 與 context 均為虛構 unit vectors，外層明示 SYNTHETIC；不得用來啟動程式或彙總原生驗收。

_validate_evidence_claim(record: Mapping[str, JSONValue], observed_bindings: Mapping[str, JSONValue], case_policy: Mapping[str, JSONValue]) -> EvidenceCheck

採 immutable input、固定第一錯誤優先序及 RFC6901 path。完整 base record、binding facts、case policy 可直接讓後續核准測試具體化，不再靠模糊文字猜預期。
