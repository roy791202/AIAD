4. Ports、所有權、Mutation與Transaction

公開兩trait／四方法維持原樣：create_directory_exclusive、acquire_write、read_current、replace_checked。receipt/error欄位未變。lease獨占OS handle；private transaction只追蹤exclusive-create取得的artifact。正式文件仍是正式資料，journal非專案SSOT。

Acquire → Validate → PrepareOld/New → PREPARED
→ Recheck → Publish → VerifyPublished → COMMITTED → Receipt
Failure → Restore → VerifyRestored → ROLLED_BACK
Unconfirmed → RecoveryRequired + retain versions + block destructive write

5. 契約與不變量

階段契約
exclusive create / acquire名稱非法 InvalidPath；存在 AlreadyExists；live OS handle Busy；無 journal 正常路徑可供後續取得；未完成/未知/損毀 journal 或有無法歸屬的 area 內容為 RecoveryRequired；不改正式檔、不清理 sidecar 或未知 area
prepare 或 PREPARED 發布前故障原 bytes/不存在維持且可證明只留下自有可診斷物時回 Storage；不確定完整性/所有權則 RecoveryRequired；不刪他人 collision；原不存在不建立正式檔；無 journal 但留有 scratch 的 area 下次 acquire fail closed
PREPARED 已有效後、publish 前偵測外部變更Conflict，保留外部版本；本次 owned 準備資料與可診斷紀錄可保留，下一次遇未終結紀錄仍 fail closed；不以 old 覆寫外部新版本
publish / verify / COMMITTED 寫入失敗先回復 old 或原不存在，再驗證，並寫入且重讀驗證 ROLLED_BACK 後回原失敗 stage 的 Storage；回復/驗證/終態記錄失敗則 RecoveryRequired；刪除新目標前須確認仍是本次 new，外部已改則拒絕刪除並 RecoveryRequired
COMMITTED 已寫且正式 new digest 驗證成功回 receipt；後續 cleanup 失敗不反轉為普通 Storage 或假稱沒提交；保留有效終態與未清資料；不在此階段回滾已成功交易
cleanup只按已驗證 terminal record/hash 清理 owned old/new；保留 journal 到 artifacts 清理完，journal 最後移除；下一次 acquire 對殘存 terminal record 只讀核對，不清理；只刪檔不遞迴；未知 entries/不相符 hash 一律不刪；只能後續 replace 的持鎖 prepare 階段完成可證實安全的 terminal 殘留清理，再開新交易
crash 與 reopenPREPARED/RECOVERY_REQUIRED/不完整 next/壞 journal 都 RecoveryRequired；有效 COMMITTED+target=new 或 ROLLED_BACK+target=old/absent 可取得 lease（僅診斷，不自動清理）；不符則 RecoveryRequired；所有不確定檔案保留；terminal 清理可能缺少 old/new，允許只在終態與正式檔吻合時忽略已刪除 artifact；仍存在 artifact hash 不符則拒絕
Invariant要求
IO-INV-1普通 Storage 不得留下未驗證的正式狀態；不能確認則 RecoveryRequired
IO-INV-2receipt 表示完整 new bytes 與有效 COMMITTED；receipt target/digests/txid 與本次提交相符
IO-INV-3不刪非本次擁有或 hash 不符的 artifact；無跨文件或遞迴 project cleanup
IO-INV-4格式驗證與 acquire 不修改原文件、journal 或未知檔；未知版本不自動遷移
IO-INV-5lease Drop/process death 後 OS handle 釋放；不按 stale age 清 sidecar
IO-INV-6journal 不能進入 M07 快照保留政策，也不能造成跨文件 Undo

  @IO-BDD-01
  規則: 獨佔建立
    場景: 獨佔建立
      假如 存在父目錄與不存在的新名稱
      當 建立目錄
      那麼 只建立該新目錄並返回位置

  @IO-BDD-02
  規則: 已有目標不變
    場景: 已有目標不變
      假如 目標為檔案、空目錄或非空目錄
      當 要求建立
      那麼 AlreadyExists；既有bytes及內容不變

  @IO-BDD-03
  規則: 非法名稱
    場景: 非法名稱
      假如 名稱空白、保留名、含separator或穿越
      當 建立目錄
      那麼 InvalidPath且不建立任何子目錄

  @IO-BDD-04
  規則: 同程序競爭
    場景: 同程序競爭
      假如 已有一個同目標lease
      當 另一adapter instance要求lease
      那麼 Busy且不能讀寫提交

  @IO-BDD-05
  規則: 跨程序競爭
    場景: 跨程序競爭
      假如 子程序持有同目標sidecar handle
      當 父程序要求lease
      那麼 Busy；不是只靠同程序Mutex

  @IO-BDD-06
  規則: 程序死亡釋放
    場景: 程序死亡釋放
      假如 子程序持有lease且無未完成journal
      當 終止子程序後再取lease
      那麼 OS handle釋放，sidecar仍可再次打開；不按檔案年齡刪鎖

  @IO-BDD-07
  規則: 新檔提交
    場景: 新檔提交
      假如 期望不存在且無目標
      當 replace_checked(None,new)
      那麼 完整新bytes與receipt相符

  @IO-BDD-08
  規則: 既有檔提交
    場景: 既有檔提交
      假如 期望digest等於現行bytes
      當 replace_checked(Some(old),new)
      那麼 寫入完整new，保留old版本直到交易確認

  @IO-BDD-09
  規則: 過期拒絕
    場景: 過期拒絕
      假如 期望digest不等於目前檔案
      當 要求替換
      那麼 Conflict，不更動正式目標

  @IO-BDD-10
  規則: 存在性衝突
    場景: 存在性衝突
      假如 期望不存在但檔案已存在，或反之
      當 要求替換
      那麼 Conflict，不能自動覆寫

  @IO-BDD-11
  規則: 替換前故障
    場景: 替換前故障
      假如 prepare/backup/temp write/sync任一步失敗
      當 結束本次提交
      那麼 原有效正式bytes不變，清理僅本次owned scratch

  @IO-BDD-12
  規則: 替換後可回復故障
    場景: 替換後可回復故障
      假如 正式replace後verify/提交紀錄階段失敗且restore可用
      當 處理錯誤
      那麼 舊bytes恢復後才可回普通Storage錯誤

  @IO-BDD-13
  規則: 回復本身失敗
    場景: 回復本身失敗
      假如 restore/restore verify失敗
      當 回傳結果
      那麼 RecoveryRequired，保留old/new/journal，後續破壞性提交拒絕

  @IO-BDD-14
  規則: 重啟遇未完成紀錄
    場景: 重啟遇未完成紀錄
      假如 上次journal未到COMMITTED/ROLLED_BACK
      當 新程序acquire
      那麼 拒絕並回RecoveryRequired，不猜測哪版應生效

  @IO-BDD-15
  規則: 未知或損毀journal
    場景: 未知或損毀journal
      假如 journal版本未知、校驗不符或含越界路徑
      當 acquire
      那麼 RecoveryRequired，保留所有原資料，不解析成可執行動作

  @IO-BDD-16
  規則: lease關閉
    場景: lease關閉
      假如 已完成lease的handle正常drop
      當 另一程序取lease
      那麼 成功；不需等待stale timeout

  @IO-BDD-17
  規則: 目標被外部改動
    場景: 目標被外部改動
      假如 prepare後偵測目標digest變更
      當 commit前重查
      那麼 Conflict且不覆寫；不聲稱防止任意非合作writer最後瞬間競爭

  @IO-BDD-18
  規則: 失敗不刪他人檔案
    場景: 失敗不刪他人檔案
      假如 owned temp名碰撞或cleanup失敗
      當 保存或中止
      那麼 不刪非本次create_new成功取得的檔；保留可診斷結果
