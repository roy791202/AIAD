意圖與假設

同一請求不重複保存；延遲成功不能越權切換目前專案。native capability、實際 caller 與 owner 生命週期仍需另包精確化。

架構與交易

UI -> authenticated Tauri command -> DispatchHost request coordination -> adopted S1/S2 -> existing IO Port
Native picker -> trusted owner-bound selection; HOST captures immutable request; S2 owns persistence outcome; UI consumes authorized projection
Reserve immutable capture -> S2 store -> retain terminal proof -> independently authorize UI binding. IO transaction boundary unchanged.

HOST owns runtime request records; domain owns definition; IO owns private journal; no new global manager or persistence store.

契約與待採納決策

RQ1 Authority
Authenticate actual caller/window and current owner before looking up a request. UI-supplied owner/session/digest never grants authority. Rejected caller cannot discover another owner result.

RQ2 Identity
Proposed key is runtime-epoch + trusted owner session + draft-id + operation + request-id. Operation is save or finalize. Native selection must already be bound to that owner. Exact issuer and owner DTO remain separate S3-G1/G2 decisions.

RQ3 Fingerprint
Compare the exact immutable typed request capture: expected revision, draft content, resolved target selection identity and prepared preference plan identity. Capture is server-owned; compare typed values, not raw JSON byte order or caller-supplied hash. Same key with changed capture is REQUEST_ID_CONFLICT.

RQ4 Reservation
Validate authority, selection and request shape, then atomically reserve the key with its capture before starting S2 store. Concurrent identical submissions observe IN_FLIGHT and do not execute a second store. Do not hold owner map locks across IO.

RQ5 Replay
Identical retained terminal capture returns the stored original outcome including commit proof; mark replayed=true. It does not re-run IO or acknowledge a newer revision. Same key with different capture is rejected even if original operation failed.

RQ6 Terminal failure
Pre-commit failure, conflict, Partial and RecoveryRequired are terminal stored outcomes, preserving the exact S2 distinction. Explicit retry requires a fresh request-id after owner refresh. Never convert committed or recovery-required evidence into ordinary unchanged failure.

RQ7 Late completion
On completion persist the terminal outcome in the retained request record before attempting UI projection. Owner switch/window closure only detaches presentation. It must not cancel or delete an already committed project. Binding is allowed only when captured owner epoch, request, draft and revision still match current authorization.

RQ8 Lifetime
Propose runtime-only records, retained until process exit without time-based eviction. Owner close revokes ability to replay; retain tombstone/result for internal completion only. No exactly-once claim across restart. Old epoch is rejected; reopen via S2 evidence and issue a new request after explicit reconciliation.

RQ9 Bounded resources
Propose at most 128 reserved request keys per owner and 1024 per process, including retained terminal keys. Refuse a new key with REQUEST_CAPACITY before IO; existing authorized replay remains available. No automatic eviction/retry or new persistent journal.

RQ10 Result projection
Proposed transport fields: requestId, operation, capturedRevision decimal string, outcome, replayed boolean, bindingStatus. outcome wraps exact adopted S2 result without discarding evidence; bindingStatus is unchanged, eligible or detached. Eligible is not itself proof a UI switch occurred. Exact DTO/error mapping remains S3-G5 work.
