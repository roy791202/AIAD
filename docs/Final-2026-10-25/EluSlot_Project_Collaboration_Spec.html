01 / SCOPE範圍與設計原則

使用者可以把既有原始碼導入為可編輯的結構，也可以由不同人分別製作架構與 UI，再用檔案交換或 Git 更新整合。任何一種模式都不應因缺少 Git 而失去 Node／Slot、UI、綁定、執行與文件交換能力。

核心決策規格
Git 是選用能力核心專案服務不依賴 GitAdapter。沒有 Git 時仍能開啟、掃描、導入、編輯、保存、匯入／匯出、建立本地快照與處理文件更新。
包含與引用分離Slot 表達真實定義歸屬或已確認的架構容納；呼叫、匯入、繼承用不同類型連線表達。
架構與 UI 可獨立交換兩者具獨立文件身分與版本；交叉關係由綁定管理，不以檔名或顯示名稱充當永久識別。
更新先預覽新增、修改、刪除、ID 重映射、受影響綁定與衝突都先呈現；不能把「匯入」默認成覆蓋。
清空有明確範圍清空架構、清空 UI、重設範例分開。預設不刪原始碼、不清 Git 歷史、不隱含永久刪檔。
驗證可重現固定範本、工作副本、情境包、預期結果與實際結果分開；模擬通過不當成真實整合已通過。
尚需由實際程式確認：現有架構／UI 格式、Runtime 能力、支援語言與可用 Host 介面。下文的檔名、服務與資料欄位為提案，不宣稱與目前程式 API 完全一致。

02 / TWO MODES無 Git 與有 Git：共同能力與差異

能力無 Git／純檔案模式有 Git／儲存庫模式
架構、UI、綁定與 Runtime完整核心功能。相同核心功能，不另做一份專案模型。
掃描與變更偵測檔案監看＋內容指紋＋語法／符號索引。相同索引，Git status／diff 額外提供版本資訊。
分工交付交換架構、UI 或綁定文件／資料包。提交與同步上述文件，也允許手動匯入。
文件更新以 documentId、revisionId、共同基準與本地草稿比對。以文件識別整合；Git commit OID 作版本來源證據，不能取代文件 ID。
衝突本地草稿衝突、同元素修改、刪除對引用、ID 衝突。前述語意衝突，加上 Git 文字／二進位／操作中衝突。
歷史與還原應用程式明確建立的快照與檔案備份；範圍須列明。Git 提交歷史與本地快照並存；未提交、未追蹤或未備份內容不保證可還原。
分支與遠端不顯示虛構分支、Commit、Push。可另選擇啟用 Git。提供分支圖、Commit、Fetch／Pull／Push 與衝突續行。

環境狀態必須分開

偵測結果UI 狀態可用動作
Git 未安裝純檔案模式 · Git 不可用核心流程照常；提供 Git 設定入口。Git 驗證標記 BLOCKED，不算通過。
Git 已安裝，目錄不是 repo純檔案模式 · 尚未啟用版本控制核心流程照常；使用者可明確初始化。
有效 repoGit 模式 · 分支／HEAD／工作目錄狀態核心與 Git 功能並存，辨識 project root 和 repo root。

純檔案工作流程

直接交換，也能保留版本依據

開啟資料夾 → 建立掃描索引 → 編輯架構／UI → 保存獨立文件 → 匯出交付 → 接收端預覽整合 → 重新驗證綁定。

保存各文件已接受的基準版本，支援有基準時的三方整合。沒有基準時退回雙向差異與人工選擇。

Git 工作流程

版本同步後，仍需理解文件內容

開啟 repo → 讀取文件 → 編輯 → 檢視／暫存／提交 → 同步版本 → 檢查 Git 結果 → 文件整合 → 綁定驗證。

Git 文字合併成功，不代表架構、UI 與綁定語意一定相容；仍走共同整合流程。

03 / CODE IMPORT程式碼導入與分層判斷

導入的目標是產生可信任的專案模型，而不是用目錄名稱猜出一棵看似合理的架構樹。語法能確認的關係與 AI／規則推論的架構意圖必須分開記錄。

層次判斷依據呈現方式
實體結構專案／套件／建置設定、資料夾與原始碼檔案。來源樹與模組邊界；檔案不一律等同業務模組。
程式結構語法樹、語言符號、定義所在範圍。模組 → 類別 → 方法，或語言相應的包含關係。
相依圖已解析的 import、呼叫、繼承、介面實作與引用。使用不同關係類型連線；共享服務不複製成多個實體子節點。
架構責任明確規則、相依方向、對外介面與語意推論。UI／服務／領域／基礎設施等分組建議，由使用者確認。
1 · 界定範圍

選取來源與排除目錄；不把套件快取、產出物或版本庫 metadata 當一般程式碼掃描。

2 · 解析結構

語法、符號與來源定位。支援能力由語言分析器回報，無法解析明示原因。

3 · 建立相依

包含、呼叫、匯入與繼承分開；循環相依保留為圖，不強制改成父子。

4 · 建議分組

結合專案規則與 AI 建議；不以 Service／Manager 等名字作唯一證據。

5 · 預覽確認

顯示來源、理由、已確認／推論／未解析，讓使用者調整粒度與容納關係。

6 · 增量維護

保留穩定對應、人工分組與來源變更紀錄；只重分析受影響部分。

Slot 的使用規則

  • 類別定義的方法可放進 Methods Slot；模組定義的類別可放進 Types Slot。
  • A 呼叫、引用或繼承 B，表示連線；不能因此把 B 放進 A 的 Slot。
  • 同一元素可在不同視圖顯示參照，但底層只保留同一身分，避免複製後失去一致性。
  • 預設展開至模組或類別，方法收進 Slot；避免首次導入就產生難以操作的大量節點。
  • 第一版為程式碼 → 模型的單向導入。拖動節點只調整視圖；搬檔、改 namespace 或程式重構是另外核對的操作。
兩種模式皆維護自己的來源索引：來源文件身分、符號識別、範圍／內容指紋、節點對應與掃描版本。索引可用於增量更新，但不是原始碼備份。

04 / DOCUMENT BOUNDARIES架構、UI 與綁定的獨立邊界

文件責任包含內容更新時應保留
架構文件Node、Slot、連線、公開端點、來源對應。UI 文件與不受影響的綁定。
UI 文件元件樹、版面、樣式、事件及可綁定屬性。系統架構與不受影響的綁定。
綁定文件／層UI 文件／元素／事件 → 架構文件／節點／端點；資料型別與方向。兩邊各自的內容；失效時保留來源證據供修復。
專案 manifest引用哪些文件、相容性／schema、專案設定與路徑。相對路徑可移轉；本機秘密與可分享設定分離。

識別與版本欄位（提案）

{
  "schemaVersion": "1",
  "documentId": "architecture-taskboard",
  "revisionId": "arch-r2",
  "baseRevisionId": "arch-r1",
  "kind": "architecture",
  "elements": [{ "id": "task-service", "type": "service" }]
}

documentId 與元素 ID 用於跨次匯入對應；revisionId 描述文件版本。Git commit OID 可以附在來源證據，不能取代跨純檔案交換所需的文件識別。不要使用「顯示名稱＋路徑」作唯一永久 ID。

獨立匯出時要帶什麼

  • 文件自身的完整內容、識別、schema 與相容性資訊。
  • 引用的資源／文件清單、可選的綁定與來源對應；缺少資源時不能假裝完整。
  • 如果只匯出架構，UI 不需要一起被複製；接收端對缺少文件的綁定顯示待處理。
  • 加入為新內容時，整套 ID 重映射包含內部連線、Slot 歸屬與內部引用；對外引用明確保留或解除。

05 / INTEGRATION & CONFLICTS共用整合流程，分別處理兩種衝突來源

取得內容

手動匯入或 Git 更新；保留來源與版本證據。

驗證與比較

格式、ID、型別、相依、共同基準與本地未儲存變更。

預覽與套用

列出新增／修改／刪除、綁定影響與衝突；核對後套用並重驗證。

匯入意圖行為必要核對
加入為新內容建立另一份文件／元素實體，與目前內容並存。ID 重映射範圍與所有引用；不能只改頂層 ID。
更新既有內容依文件身分更新；同一版本重複匯入不產生副本。共同基準、本地變更、刪除對引用與人工調整。
取代目前內容明確取代選定範圍；另一方架構／UI 保留。被刪內容、綁定影響、快照與 Undo 能力。
無 Git 的三方整合

Base／Local／Incoming

Base 是最後一次已接受、且能與接收版本確認共用的文件內容；Local 是目前含草稿的模型；Incoming 是收到的文件。

兩邊改不同欄位可提出合併建議；同欄位不同值、刪除對修改、Slot 歸屬互斥與綁定端點缺失需列為衝突。

沒有共同基準時只能做雙向差異與人工決策。不能僅憑 revision 名稱虛構 Base，也不能假設時間較新就應覆蓋。

Git 與語意雙重檢查

先辨識操作，再驗證模型

先處理 Git 的 unmerged entries 與 Merge／Rebase 等狀態；Stage 2／3 語意依操作不同，不能固定標成「我的／對方的」。

檔案可解析後，仍檢查文件 ID、Slot、型別與綁定。Git 沒有衝突標記，也可能存在模型語意衝突。

寫入後重新讀取 Git 與模型狀態；外部切分支、鎖定、Hook 失敗、timeout／取消均不能假稱已回滾。

使用者看得到的狀態

未解決 → 編輯中／尚未儲存 → 已儲存並驗證 → 可套用／可繼續 → 已完成；另有 失敗／已中止。

  • 全域提醒、檔案／元素列、逐項進度與 Inspector 使用同一份快照，不互相矛盾。
  • 重新編輯已解決結果，立即回到待儲存狀態；保存失敗保留草稿。
  • 純檔案模式的「套用整合結果」與 Git 的「繼續 Merge／Rebase」使用不同操作名稱。
  • 失效綁定可以保留文件供編輯，但依賴該綁定的執行入口不得呈現為可用；處理策略需明示。

06 / CLEAR & RECOVERY清空、關閉、備份與還原分開

操作影響範圍保留／防護
清空目前架構Node、Slot 內容、架構連線及導入對應。保留 UI、專案設定與來源檔；相關綁定標示失效；支援一次完整 Undo。
清空目前 UI選定 UI 文件的元件、版面及對應引用。保留架構；受影響綁定列出，不能靜默刪除另一方內容。
關閉專案離開目前工作階段。先處理未儲存變更與執行中工作；不等於刪除。
新增空白專案建立另一份空白文件組合。先處理目前專案草稿；原專案不被重設。
重新掃描程式碼依來源變更更新模型。保留可辨識的 ID 與人工分組，不默認清空後重建。
重設功能驗證範例僅選定的驗證工作副本。列明要重建的架構、UI、綁定、資料、索引及隔離 Git 環境；固定範本與其他專案保留。
清空前顯示實際數量與綁定影響。例如「將移除 48 個節點、12 條連線與來源對應；保留 UI、來源檔與 Git 儲存庫」。有執行中工作先阻止清空並提供 Tasks 入口。清空後專案標記未儲存。

無 Git：快照要真的包含內容

快照列出架構、UI、綁定、設定與已備份資源。原始碼只有被納入並保存內容時，才能宣稱可還原。

掃描索引、內容 hash 與修改時間只能協助辨識變更，不能還原已刪除的原始碼。

有 Git：還原要說清楚對象

Commit、Index、worktree 與未追蹤檔案分開核對。提交歷史不是未保存草稿或所有資料的保險。

一般清空架構不得附帶 reset、clean、刪 .git 或強制推送。範例重設只對明確標識的隔離副本工作。

08 / DEFAULT VERIFICATION PROJECT內建範例：Task Board 任務看板

使用一個規模小、行為容易核對的完整專案：新增任務、顯示任務清單、切換狀態與篩選。固定輸入資料與預期結果，避免依賴外部帳號、網路或付費服務。

完整驗證鏈：UI 新增任務 → 事件綁定 → TaskService 驗證與建立 → TaskStorage 保存 → 發出更新事件 → UI 清單顯示。
架構節點／Slot責任可核對結果
Application / Modules Slot容納 TaskModule、StorageModule、NotificationModule。多層容納可展開、收合與保存。
TaskModule / Services SlotTaskService 提供 createTask、setStatus、listTasks 端點。固定輸入能產生預期任務、狀態與篩選結果。
StorageModule / Adapters SlotLocalTaskStore 與可替換的測試儲存介面。重新開啟保留測試資料；寫入失敗情境可重現。
NotificationModule回報完成／失敗事件。錯誤可見，UI 不呈現虛假成功。
TaskBoard UI新增表單、任務清單、狀態篩選與詳細面板。UI 可單獨交換；綁定缺少時明示不可執行原因。

不含版本庫依賴；所有常用編輯、匯入與快照流程可單獨驗證。另準備 Git 缺失與有安裝但無 repo 的環境案例。

Git 測試副本

由同一固定基準產生隔離版本庫；用本地 bare remote 與兩個 clone 測試同步。無需外部託管服務或真實帳號；帳號驗證以另列的模擬／正式測試處理。

可重設的規則

  1. 範本不可作為日常編輯對象；開啟時建立獨立工作副本，記錄 fixtureVersion 與 workspace 身分。
  2. 重設前列出將恢復的文件、測試資料、索引與隔離 Git 環境；處理未儲存草稿與執行中工作。
  3. 只重設選定副本，不掃描後刪除相似名稱資料夾，也不把外部使用者 repo 當成範例。
  4. 固定成功資料與失敗情境分開；每個情境都有步驟與預期結果。
  5. 模擬 Agent／Runtime 可驗證 UI 狀態；真實節點執行與外部工具整合另列證據。
本 HTML 提供資料包設計與驗證清單，沒有附帶可直接執行的 Task Board 專案、Git fixture 腳本或 Runtime。這些是後續依實際檔案格式與 Host API 製作的交付物。

ProjectServiceManifest／文件 → 專案快照與版本開啟、保存、dirty 狀態與範圍操作；不直接依賴 Git。
DocumentRepository架構／UI／綁定資料 → 已驗證文件序列化、schema、穩定 ID 與原子寫入。

BindingService兩邊端點／型別／對應 → 有效／失效／衝突來源刪除、ID 重映射與更新後重驗證。

FixtureService固定基準＋情境 → 工作副本／重設計畫可辨識副本所有權；Git fixture 獨立隔離。
VerificationRunner測試 ID／環境／情境 → 結果與證據區分模擬與實機；不可執行時 BLOCKED，不假造 PASS。
Task／Event Service工作請求 → 進度／取消／完成與快照失效所有視窗訂閱相同版本；取消後重讀實際狀態。

分階段落地，但兩種模式都列入驗收

  1. 文件與識別：確認現有格式、ID、版本、綁定邊界與可分享設定。
  2. 共用整合核心：差異、基準、ID 重映射、衝突、清空與快照；建立共享測試。
  3. 雙來源接入：檔案匯入／監看與 GitAdapter 分別接入同一整合核心。
  4. 導入與 UX：掃描、分層預覽、人工確認、進度、錯誤及跨視窗更新。
  5. 固定範例與情境：同一基準產生純檔案與 Git 副本，執行下方完整測試矩陣。

可觀測事件至少包括 requestId、projectId、documentId、來源模式、快照版本、影響數量、完成步驟與錯誤分類。只記必要診斷，秘密與敏感內容不寫入一般日誌。
