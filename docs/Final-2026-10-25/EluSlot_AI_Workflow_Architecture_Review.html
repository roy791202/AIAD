01｜架構判斷

建議採用。這是一套以 EluSlot 為工作管理後端、外部 Agent 為執行端的拉取式工作流程，適合非即時、長時間、可分段驗收的工程工項。

產品核心為「規劃（架構／UI）→ Tasks 執行管理 → 接受變更 → 專案檔案更新／Git」。AI 透過 API 取得工作包，於自己的工作環境執行，再透過 API 回報進度、紀錄與結果。專案 XML 由系統管理，AI 不直接維護 XML。

關鍵條件：系統除了保存資料，還需要管理工作流程

領取、租約、合法狀態轉換、版本核對與驗收規則應由服務層統一處理。AI 回報是執行端的陳述；系統驗證與人工接受是另外兩種事實。

適合

可等待的工程任務

程式碼分析、跨節點切片、UI 實作、測試、報告與文件產出。

限制

輪詢帶來等待

五分鐘查詢無法滿足互動即時回應；需要時可使用立即查詢或通知喚醒。

核心代價

分散式一致性

失聯、重試、過期回報與檔案交付，不能只靠一個狀態欄位處理。

本文是架構設計評估與建議，並非已完成的實作或效能測試報告。所有參數為初始提案，需經實測校準。

02｜確認方向與設計假設

類別內容
已確認架構與 UI 可以獨立交換；包含槽狀結構、互動與綁定。工項以可驗收切片為單位，可以跨多個節點。
已確認Task 下保留各次 Run、Log 與 Artifact。AI 透過 API 取得工項，執行後透過 API 回報。
已確認XML 由系統管理；有 Git 與無 Git 都必須成立。五分鐘是輪詢情境，不代表心跳也每五分鐘。
假設／待定外部 Agent 有常駐程式或排程器；模型本身不負責維持永久計時迴圈。
假設／待定第一版單一可寫服務負責每個專案；Agent 的程式碼工作目錄隔離。是否要多人跨機持續服務仍待定。
假設／待定人工驗收為預設；低風險工項未來可由明確政策自動接受。遠端 Git、外網服務不是基礎流程的必要條件。

文件只評估工作流程與系統責任，不預設特定 AI 供應商、桌面框架或後端語言；也不假設「使用 XML」本身能提高模型推理能力。

API 是唯一受控寫入入口

UI 與 AI API 使用同一組應用規則。執行端不直接操作後端資料庫；API 通過驗證後才更新持久化資料。遠端 Agent 不應直接開啟共享 SQLite 或共同寫入 XML。

採用窄介面區分「查詢」「派工」「回報」「接受」「交付」，儲存與 Git 使用可替換介面。這符合單一責任與依賴反轉，也能避免 UI、資料格式及 AI 供應商互相綁死。

04｜工作流程的優點與缺點

面向優點代價／限制設計建議
規劃與執行分離更換 Agent 不必改專案資料模型規劃與程式碼可能不同步每次 Run 凍結工作包與基準雜湊
拉取式派工Agent 可依容量領取，出站連線較容易部署輪詢有延遲與空查詢提供立即查詢、退避、隨機錯開
集中追蹤從節點追溯 Task、Run、修改與證據服務中斷影響新派工持久化紀錄、備份與恢復流程
多執行端人工、CLI、IDE Agent 共用契約重複執行與同檔衝突租約、隔離工作區、整合時核對版本
結構化規劃修改範圍與介面更明確完整專案過大、語意仍可能模糊按 Task 提供切片、依賴與行為契約
有／無 Git 共用不同團隊可使用相同 Tasks 流程兩種交付仍須各自處理共用驗收，交付由不同配接器負責
完整 Log有助定位問題與重現資料成長、敏感資訊與搜尋成本結構化事件、脫敏、分頁與保留政策

不建議的情境：把五分鐘輪詢當成互動 UI 的事件處理、讓 Agent 共用一個可寫目錄、以模型自述取代測試證據，或用 Git Commit 當作功能驗收通過。

05｜五分鐘輪詢與成本

閒置 Runner 定期呼叫 API；只有成功領取工作後才啟動模型。執行中的心跳與結果回報走另一個節奏，不等待下一輪五分鐘查詢。

指標／參數估算或初始建議限制
工項發現等待固定 300 秒輪詢：約 0–300 秒，平均約 150 秒假設到達時間均勻、服務正常、Agent 有空餘容量；不含排隊與執行
單一閒置 Runner每小時 12 次；每天 288 次查詢假設連續運作且無退避
100 個閒置 Runner平均約 0.33 次／秒；每天 28,800 次查詢同時啟動仍可能每五分鐘形成 100 次突發
輪詢節奏初始每 300 秒；啟動相位隨機錯開若增加週期間隔抖動，等待範圍與平均值須重新估算
API 失敗指數退避、上限與隨機抖動；尊重 Retry-After驗證失敗或權限錯誤不無限盲目重試
執行心跳／租約例：30 秒心跳、120 秒租約示例值；需依網路、暫停與服務延遲校準
即時操作使用者按「立即派工／查詢」可喚醒 Runner按鈕不代表工項已被領取，仍需服務端確認
成本主要取決於真正執行的模型與工具

空輪詢應是輕量 API 請求，不包含模型推理。以實測 Token、工具耗時與預算限制衡量成本；不能只由輪詢週期推算 AI 費用。

選項適用情境代價
定期輪詢第一版、少量 Runner、容許數分鐘等待空查詢與等待延遲
長輪詢需要較快反應，且基礎設施支援長連線連線、逾時與代理設定成本
通知＋輪詢補漏互動性提高或 Runner 數量變多通知可能遺失，仍須可重查；第一版不必導入訊息平台

06｜系統提供工作內容，減少反覆對話

輪詢取得的工作內容由系統提供。使用者在架構／UI 與 Tasks 中完成規劃後，系統組裝工作包，AI 不必等待使用者再次貼上需求與上下文。

輪詢只是觸發取得工作的機制；真正降低溝通成本的是「規劃資料 → 可執行工作包」的組裝能力。使用者仍需定義目標、處理必要歧義與驗收結果，但不必每次重新講述專案背景。

來源系統提供給 AI 的內容
架構／槽狀結構責任、公開介面、包含關係、相關依賴與穩定 ID。
UI／互動規劃元件、事件、資料流、顯示狀態、綁定及失敗行為。
Task 定義工作目標、可修改範圍、限制、依賴與驗收條件。
版本與實際環境規劃快照、程式碼基準、相關檔案、工具版本與執行要求。
既有工作紀錄先前 Run 的失敗原因、退回意見、已確認決策與必要證據。

從人工重述改為系統組裝

  1. 使用者在規劃介面選取範圍、填入目標與驗收條件，或使用預設任務範本。
  2. 系統檢查必要資訊，收集相關節點、UI、互動與程式碼參照，產生不可變工作包版本。
  3. Runner 輪詢並領取工項；AI 依工作包執行，必要時按 ID 補取相關資料。
  4. AI 將進度、變更、證據與問題回報系統；Tasks 顯示摘要，相關節點同步呈現關聯。
  5. 使用者在介面回答待確認事項或驗收；系統保存決策並建立更新版本，後續工項可重用。
資訊不足時，回報結構化問題，而不是猜測

AI 回報「缺少資訊／等待決定」，附問題、影響範圍與可選方案。系統在 Tasks 呈現；不需保留活躍推理等待使用者。恢復時沿用經核對的執行或建立新 Run；若工作包改變，必須記錄新版本。

優點代價／控制方式
減少重複打字與上下文遺漏需要完整度檢查；欄位填滿仍不代表語意沒有矛盾。
不同 Agent 取得一致依據工作包需凍結版本，補取資料也需標示版本，避免混用新舊規劃。
決策可重用與追溯納入已核准決策，不把每段歷史聊天無限制塞進工作包。
可支援連續派工只自動派出依賴完成、已核准且範圍清楚的工項；不可把自動取得等同於無條件執行。
改善 AI 執行準確性的條件規劃需含行為與驗收；XML／JSON 的格式不能補出不存在的業務規則。

補充驗收：使用者完成一次規劃後，Runner 不經額外聊天即可取得含必要上下文的工作包；缺漏資訊會阻止派工或轉成待確認問題；回答後可恢復且有版本依據。以重複輸入次數、澄清次數與首次驗收通過率衡量效果，尚不宣稱已達成。

07｜工項工作包與回報契約

工項是可驗收的切片，不必等於一個節點。穩定引用使用「專案／文件 ID＋元素 ID」，路徑與顯示名稱只供閱讀。跨文件引用需由服務層驗證。

資料必要內容
領取的工作包Task ID、Run ID、工作包版本、規劃快照、程式碼基準；目標、可修改／唯讀／禁止範圍；驗收條件與工具需求。
領取憑證Agent 身分、租約期限、領取世代／權杖；續租與回報必須符合當前擁有權。
進度事件唯一事件 ID、Run ID、序號、階段、訊息、Agent 發生時間與服務接收時間。未知進度不顯示虛假百分比。
實際修改新增／修改／刪除的元素與檔案、前後版本、差異產出、實際影響範圍。
驗證證據指令或案例、工具與環境、結果、報告位置、對應內容雜湊；區分執行端回報與獨立重驗。
產出系統可讀的 URI／上傳 ID、雜湊、大小與格式。存在於 Agent 本機的路徑不等於已交付。
能力與容量支援語言、DCC／工具版本、作業系統、可用執行槽、可存取的專案；不得把需求不符的工作派出。

概念操作範圍（非定稿 API 路由）

操作服務端保證
查詢可執行工項僅查詢，不改變擁有權；依權限、能力與依賴篩選。
領取工項原子判定與更新；建立 Run，回傳租約。同一領取請求重送回傳原結果。
續租／批次追加事件檢查當前領取世代；事件去重與順序核對。
提交產出／結果驗證產出完整與可讀、基準未過期；相同提交重送不重複生效。
請求取消／確認停止先標記取消請求，再由 Runner 確認；無回應時標記失聯或狀態未知。
驗證／接受／退回不同權限與政策；AI 回報不能自行取得人工接受權。

冪等鍵應綁定專案、操作者、操作與內容摘要；同鍵不同內容應回傳衝突。事件依序號處理，遺漏或亂序可要求補傳，不以網路到達時間直接覆蓋狀態。API 回應成功應代表必要狀態已持久化。

08｜狀態、並行與失聯處理

層次建議狀態／責任
Task 工作流程草稿 → 可派工 → 執行中 → 待驗證 → 待驗收 → 已接受；另有受阻與取消。最新 Run 失敗不必代表 Task 永久結束。
Run 執行已領取、執行中、成功結束、失敗、取消、失聯／未知。重試建立新 Run，不覆寫前一次紀錄。
驗證未驗證、通過、未通過、受阻、已過期；綁定實際受測內容版本。
交付未套用、已套用、已保存、已匯出；Git 暫存／提交／推送另行記錄。
租約過期不代表舊程序已停止

服務可阻止過期持有者更新資料，但無法只靠 API 權杖阻止其繼續修改本機檔案。每個 Run 使用隔離目錄／worktree；整合時再次核對世代與基準。外部發布等副作用另需冪等或專用權限。

失敗情境處理方式
兩個 Agent 同時領取服務端以交易與條件更新決定唯一持有者，不能先查後無條件寫入。
領取成功但回應遺失使用原冪等鍵重試或查詢目前持有 Run，不再次建立新執行。
Agent 斷線但工作仍執行先記錄失聯；符合可安全重試政策才重派。具有不可逆副作用的工作先人工核對。
租約過期後舊 Agent 回來拒絕舊世代的權威狀態與結果；診斷資料可另存，但不得自動覆蓋新 Run。
不同工項修改同一檔案預計範圍用於排程提醒或資源鎖；實際差異仍在整合時比對基準、衝突與測試。
規劃在執行中被修改既有工作包保留快照；新結果標示基準過期，由使用者重新核對或建立新 Run。
服務重啟／崩潰從持久化交易恢復 Run 與租約；使用服務端時間判定，防止成功回應後資料消失。
取消遇到提交由服務端交易定義先後；取消後的提交不得被靜默套用。Runner 必須在提交前檢查取消。

可靠性目標：在重送與重試前提下，讓系統狀態與套用效果可去重；不宣稱整個外部分散式工作一定「恰好執行一次」。受管理的產出套用與外部工具副作用必須分別處理。

09｜XML、資料庫與 Git 的邊界

XML 可以繼續作為架構／UI 文件與交換格式；高頻的領取、續租、Log 與狀態更新，建議放在具有交易能力的執行資料儲存層。這是責任區分，不代表必須立刻採用大型資料庫。

資料權威來源建議保存／交換方式
架構、UI、互動綁定專案文件服務所管理的已保存版本XML 分文件、穩定 ID、格式版本與遷移
Task 定義與規劃基準Task 服務管理的版本可匯出交換快照；匯入不能默認變成可派工
活躍 Run／租約／事件交易式執行儲存不由 Git Merge 或直接 XML 編輯改變活躍擁有權
大型差異與報告產出儲存與雜湊資料庫存索引，內容保存於受管理檔案／物件儲存
程式碼與交付版本工作副本與交付系統Git 版本或無 Git 快照、清單與內容雜湊

避免 XML 與資料庫各自成為可寫的真相來源

第一版可維持「專案文件服務掌管規劃，交易儲存掌管執行」。建立 Task 時引用已保存的不可變規劃版本；先完成快照，再發布可派工狀態。快照未完成不得派工，孤立快照可後續清理。未來若改為資料庫掌管整個模型，XML 應成為匯出結果，需正式遷移權威來源。

部署方案適用與取捨
桌面程式內嵌 API＋本機儲存部署簡單；桌面關閉、睡眠後服務停止。適合個人驗證，不可承諾全天派工。
獨立服務＋SQLite單機／低寫入競爭可先採用；集中經 API 存取。SQLite 每個資料庫同時僅一個 writer，需壓測續租與事件吞吐。 [S1]
獨立服務＋PostgreSQL多人持續運作或寫入競爭提高時考慮。可使用交易與列鎖領取工項；SKIP LOCKED 適合 queue-like 工作，但不是全部派工政策。 [S2]

不建議把活躍執行資料庫、租約或秘密金鑰當作 Git 協作文件。Git 只傳遞歷史與專案內容，不能協調正在運作的領取權。

10｜有 Git／無 Git 的交付與恢復

步驟無 Git有 Git
建立基準保存文件版本、檔案清單與內容雜湊記錄基準 Commit；另核對未提交變更
執行隔離每 Run 建立獨立工作目錄或檔案副本每 Run 可用獨立 worktree／分支
結果提交上傳差異或結果包＋清單與雜湊提供 patch 或系統可取得的 Commit／分支；只有 SHA 不代表系統可讀
衝突判斷比對目前檔案是否仍符合基準；具備基準時做三方比對比對工作樹、基準與整合目標；Merge 成功後仍需驗證
接受與套用預檢全部變更，保存備份；以套用紀錄處理中斷與回復在受控整合環境套用或合併，保留人工變更
交付保存新版本／快照，可匯出交換包接受、保存、Commit 與 Push 為不同操作
恢復按套用清單與備份恢復；重開後能判定未完成套用使用修正提交／revert 等明確流程；不自動清除使用者修改
接受、套用與保存必須可恢復

資料庫更新與多檔案寫入通常無法共用單一交易。先持久化套用意圖與產出，再執行檔案更新，完成後記錄目標版本；崩潰後依紀錄繼續或回復。無 Git 更需要此機制。

離線檔案交換包包含文件身分、元素 ID、基準、內容與歷史證據；不得攜帶有效租約、API Token 或自動恢復活躍 Run。匯入後先核對版本與關聯，再由使用者明確選擇後續派工。

11｜Tasks、節點連動與可觀測性

位置使用者應看到
Tasks 列表工項、類型、執行者、階段、預計／實際範圍、驗證摘要、最後回報、交付狀態。
Task 詳情需求與規劃、各次 Run、結構化 Log、差異、驗證與產出；失聯與取消請求可辨識。
Diagram／UI相關 Task 徽章、對應修改部分、驗證版本；可定位到巢狀 Slot 並返回原視圖。
Git／Settings／Tasks移除固定外層 Inspector，收回欄寬；Tasks 用內部詳情區，Diagram／UI 保留屬性 Inspector。
控制面板服務連線、Agent 能力與容量、下一次查詢、最近心跳；不把 API 成功當作工項完成。

Log 採結構化追加事件，人工修正以新事件表達；可顯示人類易讀摘要，但保留原始事件與產出。第一版不必把整套系統做成完整事件溯源平台。

監測指標目的
可派工到領取的 P50／P95區分輪詢等待與容量不足
領取衝突、租約過期、失聯數識別競爭、Agent 暫停與網路問題
事件重送／去重、版本衝突確認恢復機制有效，而非靜默丟失
驗證失敗、首次接受率、重試次數衡量真正品質；不能只看完成數
API 延遲、佇列年齡、回報落後識別後端瓶頸與長期飢餓
Token、工具耗時、單工項成本限制超額消耗，判斷是否值得自動化

每筆 API 與工具紀錄串接 Project／Task／Run／Request ID。API Token 採專案與操作範圍授權，遠端連線使用加密傳輸；Log 應脫敏。文件與程式碼中的文字是工作資料，不得覆寫系統授權或擴大工具權限。

12｜實作前測試與驗收條件

以下是待執行的驗收規格，並未實測通過。正常、邊界、無效輸入與失敗情境都需覆蓋。

案例類別輸入／情境通過條件
N01正常領取符合能力且依賴完成的工項只產生一個有效 Run，工作包對應已保存版本。
N02正常執行、提交、驗證、接受與保存每階段有獨立狀態與證據，可從節點追溯。
N03正常無 Git 完整交付差異套用、快照、重開後內容與版本一致。
N04正常有 Git 完整交付基準與交付 Commit 可取得；Push 不被暗中觸發。
B01邊界多個 Agent 同時領取同一工項同一時刻只有一個有效持有者，其餘收到明確結果。
B02邊界相同領取、事件與提交各重送十次沒有重複 Run、事件或套用效果。
B03邊界租約剛到期時收到續租／結果以服務端時間與交易順序一致判定。
B04邊界兩個切片修改同一個檔案第二次整合發現基準差異，不覆蓋第一份修改。
I01無效輸入錯誤元素 ID、跨專案引用、格式版本不支援拒絕並指出原因，專案與有效 Run 不受破壞。
I02無效輸入相同冪等鍵提交不同內容回傳衝突，不沿用錯誤結果。
I03無效輸入無權 Agent 或過期租約提交拒絕權威狀態更新與套用，保留安全診斷。
I04無效輸入產出只有本機路徑或雜湊不符不能進入產出完整／待驗收狀態。
F01失敗領取已落盤但 API 回應遺失原鍵重試取得原 Run，不重複執行派工。
F02失敗Agent 失聯後舊程序恢復舊世代結果不覆蓋新 Run；隔離工作區保持分離。
F03失敗API 暫停、重啟後恢復已成功回應的狀態存在；Agent 可補傳並去重。
F04失敗取消請求與結果提交競爭狀態符合定義順序，取消後不靜默套用。
F05失敗檔案套用到一半斷電或程序崩潰恢復時辨識未完成套用，繼續或回復至一致版本。
F06失敗測試回報後內容被再次修改舊測試標為過期，不能當成新版本通過證據。
F07失敗外部部署逾時，結果未知不得自動重複部署；查詢外部狀態或人工核對。
F08失敗桌面關閉或電腦睡眠明確顯示服務不可用；不承諾繼續派工。

量化基準

  • 上述 20 項案例全部達到預期結果；Git 不可用時 N04 明確記錄跳過，其餘仍可執行。
  • 建議用 20 個競爭領取者測試同一工項，持有者永遠不超過一個；此為一致性測試，並非容量承諾。
  • 模擬重送後，系統內有效事件與套用效果數量符合唯一鍵；不可用「最後看起來正確」代替檢查。
  • 輪詢延遲與 API 延遲分開量測；測試環境、樣本量與負載固定後，再設定正式 P95 目標。
  • 每次接受皆能追到規劃基準、Run、實際產出雜湊與驗證證據；抽查完整率須為 100%。

13｜實作順序與最終建議

階段範圍完成條件
第一步：固定契約Task／Run／事件模型、基準與穩定引用、領取權限、狀態規則先定義工作包與失敗回應；不先做通用工作流編輯器。
第二步：單 Runner 閉環原子領取、租約、冪等、Log、產出、人工驗收無 Git 可完成一個跨架構／UI 的驗收切片。
第三步：可靠交付隔離工作區、版本核對、可恢復套用、Git 配接器有／無 Git 都能重現結果與回復；通過故障案例。
第四步：多 Runner能力匹配、容量、同範圍衝突、退避與監測競爭與失聯情境可控，測得真實吞吐與等待。
後續按需求擴充通知喚醒、長輪詢、自動接受政策、服務擴容由延遲、負載與維運需求觸發；不預先導入大型佇列與微服務。
建議決策

保留 XML 管規劃，API 管互動，交易儲存管執行狀態，隔離工作區管實際變更，Git／快照管交付版本。五分鐘輪詢可作第一版預設；可靠領取、版本核對與可恢復套用應從第一版就有。

下一個設計確認點是：服務是否必須在桌面關閉時仍運作、同時 Runner 數量、實際檔案在哪裡執行與交付，以及哪些結果允許自動接受。這些會改變部署與權限邊界，尚不影響本文件的責任分工。
