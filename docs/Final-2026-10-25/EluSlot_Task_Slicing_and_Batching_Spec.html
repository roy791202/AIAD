01｜切片的核心原則

以「可獨立驗收的成果」定義工作切片，以「可共用上下文的工作」組成執行批次。

EluSlot 的核心流程是：規劃（架構／UI）→ Tasks 執行管理 → 驗證與接受 → 專案檔案更新／Git。切片負責讓規劃可執行、可驗收；批次負責降低重複理解與啟動開銷。

節點是工作對象，並非固定派工單位

一個 Task 可以跨多個節點、槽、UI、綁定與檔案，也可以只修改節點的一部分。不要直接按節點數、檔案數或程式行數切分。

好的切片應能回答：做完得到什麼、如何證明正確、失敗影響哪裡、能否回復或重試。過細會放大交接與上下文成本，過大則難以定位失敗與驗收。

本文件為設計規格；尚未實作排程、模型治理或驗收執行器。案例與門檻是待驗證建議，不代表已量測的成本收益。

02｜功能目標、Task、批次與 Run

層次責任範例
功能目標描述使用者想獲得的整體能力從節點建立 Task 並追蹤執行結果
工作切片／Task定義可驗收的目標、範圍與契約保存工項與節點的穩定關聯
執行批次組合版本、權限與上下文相容的 Tasks一起完成關聯保存與雙向定位
執行 Run記錄一次實際嘗試的執行者、版本、政策與結果批次第一次執行；失敗後建立第二次嘗試
Log／Artifact保存事件、差異、測試與產出參照定位失敗原因、查閱實際修改與驗證

建議模型：Run 屬於一個執行批次，透過明確的成員紀錄關聯各 Task。單一 Task 執行也視為單成員批次；Task 可以參與多次歷史執行，但同一時間的修改擁有權必須受控。

批次共同成本只記一次。各 Task 保存實際影響、驗證與接受結果；分攤的共用成本標記為估算，不能在 Task 與批次層重複加總。

03｜派工切片的最小工作包

欄位內容派工前判斷
目標與使用情境完成後使用者／系統可做什麼不是只有「修改某節點」
範圍預計新增、修改、刪除；唯讀與禁止修改對象邊界清楚，可關聯穩定 ID
行為契約輸入、輸出、前置條件、成功與失敗行為不能只描述畫面外觀
驗收條件正常、邊界、無效輸入與失敗案例具有可觀察的通過條件
依賴先決 Task、介面、工具與資料不存在循環；先決條件已達成
基準規劃快照、程式碼／文件版本及內容雜湊來源可取得且一致
執行政策模型上限、推理強度、代理權限、重試與預算符合專案硬上限，執行端支援
回復與交付可讀的差異／結果包、套用與回復方式有 Git／無 Git 均可成立
責任與證據執行者、驗證方式、接受者或接受政策執行完成、驗證與接受分開

資訊不足時先建立「調查切片」，產出根因、介面契約或方案比較。調查有自己的驗收與上限，不可以無止境分析，也不應在未核准下擴大成整套實作。

04｜如何切分：先成果，再風險與契約

  1. 列出行為成果：從使用者動作或系統事件開始，寫出可觀察結果。
  2. 串起最小行為路徑：找出必要 UI、綁定、服務與保存層，避免只完成孤立零件。
  3. 畫清範圍與不做事項：避免工項擴張；列出允許修改與必要參考。
  4. 辨識高風險或未知：依權限、失敗影響、資料一致性與回復方式拆分。
  5. 先寫驗收：沒有可驗收條件的切片先補規格或轉調查。
  6. 估計上下文與執行需求：不是只估行數；核對模型配置、預算與依賴。
  7. 建立 Tasks，再判斷合批：保留追蹤粒度，另行優化實際執行。
情況判斷
有不同目標、可各自接受拆成不同 Task
權限、風險或回復方式不同拆開，必要時保留相依與共同交付群組
一部分已明確，另一部分未知調查與實作分開
超出上下文／執行預算尋找介面或行為邊界拆分，不機械截斷檔案
只是跨多節點／檔案不必拆，先看是否為同一個完整行為
必須一起修改才維持一致性保留同一切片，或使用受控的不可分割交付群組
每張卡重讀相同內容保留獨立 Tasks，評估合批
技術基礎可獨立驗證可另立遷移、共用介面或工具切片，附專屬測試

05｜判斷太小與太大的訊號

訊號可能問題處理
每張卡啟動與探索遠多於實作過細或批次策略不足合併相容執行，保留需要的驗收項目
多張卡反覆讀同一服務與相同規格上下文重複一次組裝必要工作包，使用相同版本
卡完成卻無法展示任何行為或契約證據以技術層切分但缺少可驗收結果改為行為切片，或補上獨立技術驗收
無法說明哪部分失敗切片過大或驗收不明確拆出可定位的行為與風險邊界
執行中持續發現不相關需求範圍失控提交新增工項提案，不直接擴大
單次結果跨越不同權限與不可逆操作失敗影響過大拆出核准點、部署或資料操作
切得更細但總成本反而上升固定開銷與返工增加比較已驗收成果的總成本，而非卡片數
不設定通用的固定行數或分鐘數

同樣十行可能是簡單文案或高風險同步邏輯。第一版使用可解釋的契約、風險與上下文規則，再以實測資料校準適合各類工作大小。

06｜完整案例：從節點建立工項

切片責任與輸入輸出依賴／驗收
S1｜建立與保存關聯使用選取節點與工項定義Task＋文件／元素 ID＋規劃版本依賴專案模型；重開後仍正確指向原節點
S2｜雙向定位Task 與節點關聯Tasks → Diagram；節點 → Tasks依賴 S1；巢狀 Slot 必要路徑正確展開，能返回原視圖
S3｜來源失效處理節點刪除、清空或文件更新保留 Task，標示來源失效依賴 S1；不誤綁同名節點，歷史證據可查
S4｜API 工作包可派工 Task＋規劃基準相關節點／UI／互動與程式碼參照依賴 S1 與 API 契約；上下文版本一致，權限正確

每個切片包含必要的跨層工作

S1 可以同時修改 UI 建立入口、服務驗證與保存層，因為它們共同完成「建立且能保存關聯」的成果。S2 不必等待 S3、S4；這些工作可在前置條件完成後依衝突與容量排程。

若穩定 ID 契約尚不存在，可先增加技術切片「建立文件／元素識別契約」，以唯一性、往返保存與引用驗證作為驗收，不能把隱含前置工作留給實作者猜測。

07｜合批方式與部分成功

檢查允許合批條件拒絕或拆批條件
上下文共用主要模組與必要依賴不相關內容太多，超出工作包上限
版本基準相容；依賴順序可明確執行來源版本互相衝突
權限同一執行環境可合法完成全部工作不同資料權限或隔離需求
模型存在對所有成員都合規且足夠的配置部分 Task 禁止使用批次需要的等級
風險與回復可獨立驗收，失敗影響可界定無法部分回復或產出無法分辨
成本共用開銷可降低，總預算足夠為了合批而擴大模型權限或預算

案例：Git／Settings／Tasks 移除 Inspector

可建立三張驗收卡，共用主視窗版面策略的一次執行。各卡檢查頁面欄寬、切換與返回狀態；必要的共用回歸檢查執行一次並關聯到所有適用卡。

接受與套用可能需要共同邊界

若三張卡依賴同一不可分割的共用修改，系統應標示共同套用／接受群組，不能假裝能任意只接受其中一份程式差異。若成果可安全分離，才支援部分接受。

批次部分失敗時，記錄每個 Task 的結果及實際範圍；續行前比對目前基準，對變更過的共用內容重驗必要案例，不盲目重跑已接受的全部工作。

08｜燈號預設與 Task 個別資源限制

燈號提供階段的基礎規範；Task 欄位提供精準限制。切片大小與模型配置相關，但不可只靠顏色判定難度。

層次規則
專案硬上限允許模型、總預算與代理最高權限
燈號預設依階段帶入模型／推理／代理與啟動規則
Task 個別設定繼承或覆寫燈號預設，但不能超越專案硬上限
批次有效政策所有成員限制的共同可行範圍；無共同配置就拆批
Run 凍結配置記錄政策版本、模型與基準；執行中不偷偷換資源
已討論的工作狀態基礎策略
橘燈：等待測試Runner 執行／等待，不維持模型空轉
橘燈：依明確規格補測試、整理結果預設較低成本模型，單代理
紅燈：未知原因或複雜問題診斷允許較強模型做定位，仍需預算與證據
診斷後修正方式已明確可由合規的一般模型實作，再回到測試
灰燈／黃燈可設定基礎政策；目前業務定義與等級對應未完整確認

模型上限代表允許最高等級，不要求一定用到最高。等待使用者或核准時先暫停，不因 Task 允許高階模型就啟動。換燈、重試、拆分與合批均不能默默重置已消耗預算；調整分配需保留總帳與來源關係。

09｜誰負責切片與派工

系統規則初分 → AI 提案 → 系統檢查與政策核准 → 可派工 → Runner 執行與回報。

模組責任輸入 → 輸出依賴
規劃服務收集架構、UI 與行為選取範圍 → 規劃版本與相關資料專案模型／XML 管理
切片建議提出成果、邊界、依賴與理由目標 → Task 草案規劃與已核准決策
派工檢查驗證完整度、循環依賴、權限與可執行性草案 → 可派工或待確認政策與能力資料
批次規劃以規則合併相容工項可派工 Tasks → 成員與執行順序版本與修改範圍
Runner領取、套用限制、執行與保存檢查點工作包 → Log、差異、產出API／執行端配接器
驗證與交付核對實際範圍與逐項結果產出 → 接受、退回、套用與保存測試／檔案或 Git

第一版以規則與範本為主；AI 負責建議，不能自行無限制新增可執行工項、擴大範圍或派生代理。執行中發現需要拆分時，提交提案、證據與剩餘工作，由系統依政策核准。

同一 Task 不能因重新切片就失去原始需求與成本。原工項保存「被取代／拆分」關係、已完成成果、歷史 Run 與剩餘驗收；新工項引用原基準並核對是否過期。

10｜有 Git／無 Git 的共同切片規則

面向無 Git有 Git
執行基準文件版本、檔案清單與雜湊Commit＋必要的工作樹內容狀態
工作區每 Run 隔離副本或目錄每 Run 隔離目錄或 worktree
差異交付系統可取得的結果包／patch系統可取得的 patch／Commit
衝突檢查目前檔案與基準比較整合前比對工作樹、基準與目標分支
接受與保存逐項／群組接受，受控套用與快照逐項／群組接受，再套用、提交與選擇同步
恢復備份與套用清單，崩潰後恢復明確修正或回復流程，不擅自清除人工修改

兩種模式使用同一份 Task、驗收與資源政策。Git Commit 不是切片完成證明，無 Git 也不能缺少版本與差異證據。共同修改需要共同套用時，兩種模式都應明確標示。

11｜實作前測試與驗收條件

以下 16 項均為待實作的驗收規格，不是既有功能的通過紀錄。

案例類型情境通過條件
S01正常單一成果跨 UI／服務／保存同一切片驗收完整行為，不因跨檔自動拆分。
S02正常技術基礎切片有獨立契約與測試，後續依賴清楚。
S03正常三張相容卡合批共用上下文，逐項結果與成本彙總不重複。
S04正常調查切片產出定位證據或契約，達標後停止。
S05邊界工項只改節點一部分範圍可定位到屬性／方法／介面，不標整節點完成。
S06邊界不同模型上限的 Tasks僅共同合規且足夠的配置可合批，否則拆開。
S07邊界批次共同差異無法安全拆開標示共同接受／套用群組，不允許假部分接受。
S08無效缺少驗收或基準不可派工，指出缺漏或轉為待確認。
S09無效Task 依賴成環阻止派工並指出相依路徑。
S10無效引用失效或越權目標拒絕或要求重新對應，不用同名自動替代。
S11失敗執行中發現額外需求保存提案，不自動擴大原工項。
S12失敗批次部分失敗保留逐項結果，續行核對基準與必要共用回歸。
S13失敗切片超預算後拆成新卡保留來源與已耗額度，不能取得免費重置預算。
S14失敗產出後基準被人工修改標記衝突或過期，不能覆蓋目前版本。
S15狀態橘燈只是在等待測試Runner 等待，不啟動模型推理迴圈。
S16相容有 Git／無 Git 往返交付保留 Task 關聯、驗收與可取得的版本證據。

量化評估

  • 完整度：可派工 Tasks 必須具備目標、範圍、基準、驗收與有效政策；缺少任一項就不能自動執行。
  • 可追溯性：接受成果都能追到規劃版本、Task、批次、Run、產出與受測版本。
  • 成本：以每個已驗收成果的總成本衡量，包含調查、失敗、重試與審查；共用成本只計一次。
  • 品質：首次驗收率、返工率、失效引用與越界修改，作為省量不可犧牲的指標。
  • 時間：分開量測排隊、模型、工具與人工等待，避免把五分鐘輪詢延遲誤判成切片問題。
  • 人工負擔：記錄每個成果需要的澄清與核准次數；不以工項數量或卡片越小作為成功標準。

用固定專案基準比較「每卡獨立執行」與「追蹤分卡、相容合批」，重複測量成本與品質；尚未實測前不承諾固定省量比例。

12｜建議導入順序

順序交付內容完成條件
1｜固定切片契約Task 必填欄位、類型、依賴、穩定引用與基準缺漏與非法關聯會阻止派工
2｜單卡閉環工作包、Run／Log、差異、驗證、接受與保存有／無 Git 可重現同一個行為成果
3｜規則式合批相容檢查、成員順序、逐項結果與共同交付群組部分失敗不造成假完成或成本重複
4｜資源政策燈號預設、Task 上限、執行端能力核對與預算繼承拆分、重試、換燈不繞過上限
5｜用實測校準各類工作大小、模型配置與合批效果以已驗收成果的成本與返工決定調整
建議的產品行為

讓使用者定義目標，系統與 AI 提出可解釋的切片與批次；使用者只需處理必要歧義、風險與例外。追蹤可以細，執行不必碎。

依據：本輪對話已確認的產品方向與架構建議。尚待決定：灰燈／黃燈的完整語意、模型等級清單、預算數值，以及哪些工作允許自動接受。
