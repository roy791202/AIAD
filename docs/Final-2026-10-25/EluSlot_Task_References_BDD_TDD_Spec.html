01｜設計決策與適用範圍

規劃是藍圖，Tasks 是執行與交付單位；BDD 定義行為，測試提供證據。以版本化引用連接，各自獨立保存。

Task 應提供正式的引用功能，讓使用者與 AI 清楚知道實現什麼、可修改什麼、需要參考什麼、以什麼驗證。系統再由引用組裝工作包，減少重複向 AI 說明上下文。

關聯不等於資料內嵌，也不等於修改權限

不把 Task、Scenario 與測試紀錄塞進架構節點。各對象具有穩定 ID；引用只建立語意關係，實際修改仍須通過專案政策、角色與執行端權限檢查。

本文件為設計規格，含提案欄位、行為規則與待驗收案例，不代表系統已實作。欄位識別與狀態名稱可於正式介面設計時確認。

02｜資料責任與解耦關係

對象責任與其他對象的關係
架構／UI 藍圖定義節點、Slot、介面、UI 結構與互動供 Task 參照，不因工項存在而被鎖死
Task定義可驗收工作切片、範圍與資源政策可引用多個藍圖元素，也可為專案層工作
BDD Scenario描述具體行為與成功／失敗情境一個 Task 可包含或引用多個 Scenario
Test Case定義測試資料、操作與斷言可驗證多個 Scenario 或介面契約
Run／測試執行保存一次嘗試的結果、版本與證據同一測試可執行多次，不能覆寫歷史
引用關聯保存來源、角色與版本依據連接對象，供查詢、工作包與影響分析
Artifact保存差異、報告、快照與產出內容以參照與內容雜湊關聯執行紀錄

同一節點可能有「切片 A 已接受、切片 B 執行中、切片 C 尚未開始」。不得以單一 Task 完成推導整個節點完成。節點顯示摘要與版本有效性，完整結果以工項與驗證紀錄為準。

節點刪除或藍圖清空時，歷史 Task、Scenario、測試與證據保留。文件或環境維護工項可以沒有節點關聯，但仍需目標、範圍與驗收依據。

03｜Task 引用角色

角色可引用對象用途與權限
實現目標節點、UI、互動／Scenario說明要完成的能力，不自動授權修改
可修改範圍節點、Slot、介面、綁定、程式符號或檔案列為預計變更邊界，仍受專案硬限制
唯讀依賴模組、契約、參考文件、相關程式碼允許讀取作為依據，不授權寫入
驗證依據Scenario、Test Case、規範定義必須符合的行為與檢查
前置工項其他 Tasks 與必要產出建立依賴，不等同內容引用；必須檢查循環

實際影響由執行結果另外保存，不覆寫原先的可修改範圍。超出預計範圍需申請擴權或新工項，不能執行後才補一筆引用當作已授權。

同一對象可具有多種角色，但唯讀與可修改衝突時必須明確解決；專案禁止範圍優先，不以寬鬆角色自動覆蓋限制。

04｜引用資料欄位與狀態

欄位責任
Reference ID識別關聯本身，支援新增、修改與刪除歷史
來源專案／文件 ID定義來源身分；跨專案引用需額外權限
來源元素 ID／子範圍定位節點、方法、屬性、Slot、綁定或文件段落
目標種類與引用角色區分對象類型、實現／修改／依賴／驗證意圖
基準版本／內容雜湊識別派工使用的確切內容，必要時保留不可變快照
顯示名稱與路徑方便閱讀與導覽，不作唯一識別
建立者與決策紀錄留下誰引用、為何引用與核准依據
解析／版本狀態系統行為
有效且版本一致可依引用角色提供工作包資料
來源已更新歷史基準仍保留；顯示變更並進行影響檢查
來源不存在保留歷史身分，不自動改綁同名對象
無權存取不得外洩來源內容；提示需要授權或替代依據
版本不可取得阻止依賴此版本的自動派工或套用
待重新對應由使用者選定新來源，建立有記錄的新引用版本

解析狀態、版本新舊與權限可分別保存，避免單一狀態掩蓋多個問題。相同穩定 ID 仍可能介面已變更，不能只因 ID 存在就判定工作包有效。

05｜使用者操作與雙向定位

入口操作預期行為
Task → 引用區搜尋／選取來源，指定角色與範圍預覽內容與版本；儲存引用並檢查衝突
Diagram／UI從選取元素建立 Task帶入候選引用，讓使用者確認角色，不預設全部可修改
Task → 引用項目定位來源切到原編輯器，展開必要 Slot；保留返回位置
節點／UI → 相關工項查看引用自己的 Tasks按引用角色、狀態與版本篩選
Task → 版本差異查看引用來源更新顯示影響與待決策項，不默默替換執行依據
Task → 調整範圍移除引用或重新對應修改草稿／建立新工作包版本，不改寫歷史 Run

Task 詳情可分「需求與 BDD、引用、測試設計、執行／驗證、變更／交付」。Tasks 列表以摘要顯示 BDD／TDD，展開列或詳情區編輯完整內容，避免主表格無限制橫向增長。

06｜BDD：Scenario 與步驟欄位

介面欄位內容保存規則
Scenario案例名稱、行為目標與必要說明具有穩定 Scenario ID 與規格版本
Given初始狀態與前置條件步驟型別為前置條件
And補充前置條件繼承前一個 Given 類別
When觸發動作或事件明確主要觸發點
Then可觀察結果與狀態變化可拆成多個斷言所需行為
And補充預期結果繼承前一個 Then 類別

使用者提出的欄位可呈現為「Scenario／Given／And／When＋／Then＋／And＋」；其中 ＋ 是新增步驟操作，不是欄位識別的一部分。

底層採有順序的步驟清單，每筆保存 ID、關鍵字、語意類型與文字，不設固定數量的 And 欄位。沒有前置步驟的 And 不合法；新增動作也須保存清楚順序。若包含多個獨立觸發與獨立成果，優先拆成多個 Scenarios。

規格狀態與執行狀態分開

Scenario 的草稿／核准與測試的待執行／通過是不同概念。Given／Then 記業務狀態，不拿來記錄測試目前綠燈或失敗。

07｜TDD：測試設計與執行循環

區塊欄位責任
測試設計Test Case、關聯 Scenario、類型、位置描述要測什麼、在哪裡執行
測試設計Arrange資料、環境、依賴與初始狀態
測試設計Act觸發方法或操作
測試設計Assert＋一項以上可檢查的斷言
TDD 摘要Red有效的目標行為失敗與證據
TDD 摘要Green實作後測試通過與受測版本
TDD 摘要Refactor整理理由、修改與重驗；可標示不需要
執行摘要Result未執行、執行中、通過、失敗、受阻；過期與不穩定另作有效性／品質標記

Arrange／Act／Assert 是案例內容；Red／Green／Refactor 是開發循環，分開保存。TDD 欄位顯示摘要，每次實際執行建立獨立紀錄並保留 Run、指令、結果、報告與內容雜湊。

Scenario 與 Test Case 採多對多映射。映射可細到 Scenario 步驟／預期結果，避免一條粗略關聯被誤當整個案例已覆蓋。沒有自動化測試的部分必須列明人工檢查與證據，不能算作自動通過。

BDD 描述應發生的行為，TDD 提供可執行檢查。綠燈只對已測範圍及當時版本有效，不能證明不存在其他需求或錯誤。

08｜每個切片的完成判定

關卡必要條件未符合時
派工準備目標、引用、行為、基準、驗收與資源政策齊全待補資料或調查，不自動派工
有效 Red失敗源於目標行為缺口，而非語法／環境故障環境或測試受阻，不算 Red 完成
Green新增／修改測試與必要既有檢查通過保存失敗，依限制修正或診斷
Refactor需要時整理並重驗；不需要則說明不得為填欄而無意義重構
範圍核對實際差異符合已核准可修改範圍越界需核對或退回
驗證有效性測試對應欲交付內容，必要回歸與人工檢查完成舊證據過期或有缺口則不能接受
接受符合接受政策，人工或授權規則作決定保持待驗收，不由 AI 自述宣告完成
交付產出可取得，套用保存完成並有版本記錄已接受與已交付分開顯示

例外與防止假通過

  • 既有測試已涵蓋、純調查或文件工作，不硬造 Red；以明確的適用性、替代驗證與核准依據記錄。
  • 同版本忽過忽敗標記不穩定；保留所有執行，不重跑到成功就當作穩定通過。
  • 刪除斷言、跳過案例、改變預期行為或測試範圍，需理由與差異，依政策核准。
  • AI 回報通過不是證據；Runner 收集結果，必要時在獨立受控環境重驗。
  • 程式或測試內容再次變更，依影響標記舊結果過期；改名等無關變更也需明確的有效性判定，不自動全綠。

09｜版本、上下文與 AI 執行政策

  1. 草稿：使用者可查看來源最新內容，系統提示引用是否更新。
  2. 派工：凍結 Task、BDD、測試設計、引用與程式碼基準，生成工作包。
  3. 執行：AI 依 API 按 ID 補取所需資料；補取結果記版本，不混用無法辨識的新舊內容。
  4. 來源改變：保留舊基準並分析影響，不直接改寫正在執行的 Run。
  5. 重新核對：需要時建立新工作包／Run；預算與歷史不可因重開執行而清零。
  6. 整合：核對目前版本、實際差異與受測結果，過期或衝突則退回處理。
工作狀態模型與程序策略
橘燈：等待測試Runner 執行或等待，不維持模型推理
橘燈：明確補測試／整理結果依政策使用較低成本模型，限制派生
紅燈：未知原因／複雜問題診斷允許較強模型，附證據且受總預算限制
所有狀態Task 可個別設定模型上限；不能突破專案硬上限。燈號只提供預設政策。

工作包不是把所有引用全文一次塞入。系統提供必要契約與相關片段，其他資料按需取用。必要依賴缺失會增加猜測風險；無關資訊過量則可能淹沒重要要求。引用完整度檢查是最低門檻，不保證模型不犯錯。

11｜待驗收案例與量測

以下 18 項為功能實作前的測試定義，尚未執行。

案例類型情境通過條件
R01正常從節點建立 Task帶入候選引用，角色經確認，不預設全部可修改。
R02正常Task 搜尋並新增引用保存穩定 ID、角色與版本，可雙向定位。
R03正常一個 Scenario 對多個測試可追查每項必要結果的檢查依據。
R04正常多次 Red／Green保留每次結果，摘要指向正確版本。
R05邊界來源改名／移動仍依 ID 解析，不因顯示路徑改變而接錯。
R06邊界來源刪除後出現同名節點舊引用失效，不自動改綁。
R07邊界來源更新但 ID 相同標記版本改變，進行影響檢查。
R08邊界唯讀／修改角色衝突要求解決；禁止範圍不能被寬鬆角色覆蓋。
R09無效And 沒有前置語意步驟阻止不完整規格進入可派工。
R10無效錯誤 ID、跨專案無權引用拒絕解析／讀取，不外洩內容。
R11無效基準版本已不可取得阻止依賴此基準的自動執行。
R12失敗Red 其實是缺少套件標記環境受阻，不算目標行為失敗。
R13失敗重跑到綠但同版本忽過忽敗保留不穩定標記與所有執行，不能掩蓋失敗。
R14失敗AI 刪斷言或跳過必要案例顯示規格差異，未核准不得接受。
R15失敗測試後程式碼改變舊證據依影響過期，必要時重新執行。
R16失敗實際差異超出允許引用範圍阻止自動套用，需申請或退回。
R17例外Refactor 不需要或調查無 Red明確記適用性與替代證據，不偽造循環。
R18相容有 Git／無 Git 交付都能追溯引用、Run、受測內容與交付版本。

量測要求：接受結果須能追到引用基準、Scenario／替代驗收、測試或人工證據與受測版本；越權引用不得被解析成可寫範圍；歷史執行不因重試遺失。以未覆蓋行為數、失效引用、返工與人工澄清次數評估改善，不用「全部綠燈」代替證據完整度。

12｜Log 介面：誰查閱、領取與提交

產品需要可查詢的 Log 介面，追蹤誰取得工項、誰執行與誰提交。單有最新狀態不足以說明工作流發生了什麼。

本文將使用者的「提取／交」理解為工項領取與結果提交；同時區分查閱、領取、提交、接受與交付。查詢內容不代表取得執行權，提交也不代表已被接受。

事件需要記錄的事實
查閱／取得工作包誰讀取哪個 Task／工作包版本；高頻空輪詢採統計，不逐筆淹沒任務時間線
領取／續租實際 Agent 身分、Runner／裝置、Run、領取世代與有效期限
開始／進度／受阻階段與有意義的進展，發生時間與服務接收時間
提交／重試誰提交哪些產出與版本、請求是否去重、服務是否接收或拒絕
驗證誰或哪個驗證器執行、報告與受測版本；區分執行端自述與獨立重驗
接受／退回操作使用者或核准政策、理由、依據的結果版本
套用／交付實際保存者、檔案版本或 Git 參照、成功／失敗與恢復紀錄
引用／規格變更誰修改引用、BDD、測試預期或修改範圍，以及核准理由

事件詳情展開結構化摘要、產出與版本參照、拒絕原因與關聯 Request ID

每筆事件的必要欄位

Event ID、Project／Task／Run ID、事件類型、服務端確認的 Actor ID／類型、Agent／Runner ID、Request ID、來源與目標版本、服務端時間、執行端時間、結果／原因、產出參照。模型名稱可補充，但不是領取者身分。

稽核身分由服務端判定

呼叫者身分取自驗證憑證，不採信 AI 自填「我是誰」。UI 代操、Agent 代表某使用者執行時，分別記錄執行者與委派者；失敗或拒絕的領取／提交也要可追查。

Log 採追加事件，修正以新事件表達，不允許執行端覆寫舊紀錄。重要狀態與稽核事件需一併可靠持久化；介面可先提供輪詢更新，不必先建即時推播平台。敏感憑證不入 Log，依專案權限顯示；API 自由文字是未信任資料，不能被當作系統規則。

避免介面噪音：心跳顯示最近時間與健康摘要，空輪詢顯示統計；領取、失聯、提交、拒絕與核准事件完整可查。事件分頁與日期篩選，保留／封存政策需明確，不宣稱無限或防竄改保存。

補充待驗收：可查出任一 Task 的有效領取者與各次提交者；兩個 Agent 競爭可見成功與拒絕；重送不產生重複業務事件；偽造 Actor 欄位無效；來源刪除仍可查歷史；無權使用者不可讀取他人專案紀錄。

13｜建議實作順序與模組邊界

模組責任輸入 → 輸出依賴
引用服務穩定解析、角色與版本核對Reference → 來源／狀態／差異專案模型與權限
BDD／測試規格服務管理 Scenario、步驟、Test Case 與映射規格編輯 → 有版本的驗收依據穩定 ID 與規格驗證
工作包服務按引用組裝必要上下文Task＋規格基準 → 不可變工作包引用服務與執行政策
執行／驗證服務保存結果、判斷有效性與受阻Run／報告 → 驗證摘要與證據Runner 與產出儲存
接受／交付服務檢查切片完成與受控套用有效成果 → 接受／保存／交付版本檢查、檔案／Git 配接器
  1. 先做 Task 引用、角色、搜尋與雙向定位。
  2. 加入基準凍結、來源更新與失效處理。
  3. 完成 BDD 步驟、測試設計與穩定映射。
  4. 串接 Runner 證據、Red 有效性與測試版本有效性。
  5. 加入切片完成關卡，再擴充批次與共同交付驗收。
最終產品原則

藍圖指導工作，Task 明確引用與授權範圍，BDD 定義行為，測試提供版本化證據。各對象解耦保存，透過關聯讓使用者與 AI 取得一致的工作依據。

有 Git 時附提交與工作樹依據，無 Git 時保存文件版本、快照與雜湊。XML 由系統維護，AI 使用 API 讀取與回報。本文整理本輪已確認方向；具體 UI、欄位 ID 與例外核准政策仍可在實作前確認。
