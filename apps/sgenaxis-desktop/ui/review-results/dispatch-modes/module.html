CLI 派工與 Agent 接入

PD-RUST-DISPATCH-MODES-PLAN-01 · PLANNING · ADR Proposed · ARCHITECTURE_NOT_READY · Implementation NOT STARTED · Tests NOT RUN

目的：讓正式 Rust 產品支援「產品啟動 CLI Agent」及「外部 Agent 透過 MCP 取得工作、回報結果」，共用任務、租約、Guard 與證據規則。Agent 執行完成只代表回報到達，不能自行宣告產品 GREEN。

規劃日期 2026-10-25 Asia/Taipei。以下為待核准設計；沒有新增正式 Port、啟動服務或連線。module-spec 為本提案的結構資料，畫面為其人工審閱投影。

三個獨立選擇

軸選擇意義
派工權責產品啟動 / Agent 領取前者由產品建立 Run 並啟動程序；後者由已連入 Agent 領取已核准任務。MCP 本身不會讓 Agent 自動持續執行。
傳輸介面CLI command / MCP；HTTP API 待決策回報 command、MCP tool 或 HTTP 都必須轉成同一組 Application commands；不能各自維護任務狀態。
程式部署桌面／常駐 Host / Agent 啟動 headless 子程序使用者已澄清「掛在 Agent」指像 Figma 一樣在 Agent 視窗顯示與操作產品。建議新增 embedded Web workbench driving adapter，共用 Rust core；後端 MCP tools 與畫面宿主分開評估。不是直接嵌入原生 Tauri 視窗，也不需新增第三個 AgentProvider。

現況與改動邊界

正式來源：apps/sgenaxis-desktop/crates/sgenaxis-exec/src/port.rs 的 AgentProvider::{Cli,Mcp} 與 AgentPort，是產品呼叫外部 Agent／工具的 outbound 執行介面。src-tauri/src/dispatch.rs 的 DispatchHost 持有 Engine、WORK、SPEC、EVID、FLOW、Run 與 lease，且目前宣告單一 in-flight Run。

新增 Agent→產品 MCP 是 inbound driving adapter，不可把它直接塞進既有 outbound McpAgentAdapter。單一 Run 限制先保留；多 Agent 並發執行能力另立架構決策，不由本提案暗中放寬。現有 Fake MCP 不構成 Live 驗證。

A10–A14：狀態、Mutation、Transaction 與外部邊界

State ownership：沿用產品 WORK／SPEC／EVID／FLOW 權威狀態；Agent 只持任務快照與回報，UI 與 HTML 為投影。Run 綁定 project root、work item、worktree fingerprint、approved envelope revision、lease identity 與 execution identity。既有 RunId 僅 u64，不假設可跨重啟唯一；持久化 identity／generation 策略必須先定案。

Mutation boundary：所有外部輸入經 adapter 驗證身份與資料格式，再交 Application 重新驗證核准狀態／lease／fingerprint，才可變更產品狀態。Agent 自報「approved」不能構成授權。直接檔案寫入、直接改看板、跳過 Guard 均禁止。

領取交易：讀取核准 revision → 驗證 Guard / worktree → 原子取得 lease + 建立 Run → 回覆
CLI 啟動：先建立受控 Run → spawn → 成功綁定；spawn 失敗則終止 Run 並釋放 lease
回報交易：驗證 identity / lease / revision → 去重 → 儲存 evidence → 記錄 provider terminal
                                                           ↓
                                                 FLOW 仍須獨立驗收
任何拒絕：不更改既有 Run／證據／FLOW

Lifecycle：Proposed Created → Running → Reported／Failed／Cancelled／Expired。心跳不等於授權延期；期限、重連、取消、Host crash 回收規則尚待決策。晚到／重複回報必須有明確結果，不能復活已過期 lease。headless exit 不等於工作完成。

External boundary：Agent 與子程序是不可信執行者；MCP／HTTP 只提供操作入口，不能授予架構核准權。命令回報使用結構化檔案／stdin，避免把 Agent 文字當 shell 執行。

Forbidden dependencies：Domain→Tauri/MCP/HTTP/OS/SDK；Adapter→直接改 Domain 可變狀態；Agent→權威庫直接寫入；一個 Host 之外另建獨立可寫 SSOT；report→自動 green；inbound MCP→冒充 outbound AgentProvider。

命令與回報流程

產品啟動 CLIAgent 主動連入 MCP
UI 選已核准任務 → Application 驗證 → 建立 Run/lease → AgentPort 啟動 CLI → CLI 回傳事件；若需外部 report command，也只能提交同一 Run 的證據。不能只靠 exit 0 驗收。Agent 查詢可領任務 → claim → 取得受限 envelope 與 lease → Agent 自身決定執行排程 → heartbeat → submit_report → 查詢入庫結果。MCP server 不在背後偷偷啟動另一個 Agent。
API、command 與 MCP submit 都映射 SubmitRunReport；相同 idempotency key＋內容應回相同入庫結果，不同內容衝突必須拒絕。具體 key、sequence 與 error code 待契約核准。

ADR：將產品掛在 Agent 的部署選擇

Status Proposed；Decider 專案 Owner。建議先採「Agent 註冊產品 MCP tool server，連回同一 Rust Host」以保留單一 SSOT。若選 Agent 自行啟動 headless Rust，必須確認它是轉送同一 Host 的薄入口，或是唯一權威 Host；兩者不能同時寫不同狀態。

方案優點代價／未解問題
A 桌面／daemon Host + Agent MCP toolUI、CLI、Agent 共用生命週期與既有狀態。Host 需可被連線；離線／身份驗證與服務啟停待定。
B Agent-spawned headless，代理至同一 HostAgent 可管理 transport 子程序；SSOT 保留。Host 不可用時明確失敗；不能在本地悄悄建第二庫。
C Agent-spawned headless，唯一權威 Host不依賴桌面常駐。Host 選主、UI attach、重啟持久化、並發身份及租約恢復均屬新增架構，成本最高。

Measurable acceptance proposal：三種入口共用相同核准與證據判定；未核准請求零狀態變更；同工作並發 claim 僅一個成功；重送不重複 evidence；失效 lease 回報不能更新 FLOW；Provider 成功不自動 GREEN；全部已核准 BDD 有 executable evidence；架構 review 無禁止依賴。這些仍待 Owner 確認。

使用者澄清：像 Figma 一樣在 Agent 視窗操作

可行方向是 共用 Rust core + inbound MCP tools + embedded Web workbench，桌面 UI 保留為另一個 driving adapter。嵌入 Web 畫面經 MCP tool 或 command/API adapter 呼叫同一 Application ports；不能自己維護第二份任務狀態。

平台層面有官方能力依據：ChatGPT UI 說明 MCP server 提供 UI resource、Web iframe 與 MCP Apps bridge；Extensions 說明 Sidebar apps 與 conversation panels。這支持此方向的可行性，不能證明目前 Codex 帳戶已能安裝或操作這個產品。

官方 quickstart 的遠端 ChatGPT 開發模式需要可連線的 public HTTPS /mcp。現有 127.0.0.1:8770 靜態頁本身不構成 Agent UI 整合。本輪沒有開 tunnel、部署公開端點或驗證 native Tauri embedding。
