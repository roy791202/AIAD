Filesystem persistence: minimal safe-write proposal

[Phase: Green] [Status: OK] OWNER_APPROVED_A — verified RED completed; final helper implemented; independent focused13/workspace290/EXEC56/Tauri79 PASS; architecture review PASS; owner acceptance pending.

Keep the existing FileSystemPort. Fix only the real adapter’s shared temporary path and failure cleanup. No new patterns or layers.

Two architecture views

UI / CLI driving adapters
  ↓ existing HOST use cases (application)
  ↓ FileSystemPort input boundary
  ↑ StdFileSystem driven adapter implements port
  ↓ std::fs / OS
Domain: no filesystem dependency
HOST ──depends──► sgenaxis-ports ◄──implements── sgenaxis-adapters
                                                    │
                                                    ▼
                                                  std / OS
Transaction: exclusive sibling → write → sync → close → rename(commit)
Failure before commit: target unchanged; cleanup owned temp only

Architecture A1-A14

A1 System context

Existing HOST document/settings save callers invoke FileSystemPort. Only real StdFileSystem implementation changes; no UI or generic save redesign.

A2 Hexagonal system boundary

Driving UI/CLI -> existing HOST use cases -> FileSystemPort <- StdFileSystem -> OS filesystem. Domain has no filesystem dependency.

A3 Module dependency

HOST -> sgenaxis-ports; sgenaxis-adapters -> sgenaxis-ports and std. No application -> concrete adapter dependency added.

A4 Responsibilities

Caller owns save intent and payload. FileSystemPort owns opaque IO contract. StdFileSystem owns one write transaction and temporary file lifecycle. OS implements rename.

A5 Input ports

Existing FileSystemPort::write_atomic(path:&str, contents:&[u8])->Result<(),PortError>; no signature changes.

A6 Output ports

No new output ports; adapter calls std::fs/OpenOptions/Write behind existing IO boundary.

A7 Driving adapters

Existing UI/CLI/HOST callers unchanged; tests call FileSystemPort.

A8 Driven adapters

StdFileSystem only. FakeFileSystem unchanged; real adapter tests establish OS-specific guarantees.

A9 Dependency direction

Caller -> existing port <- real adapter -> standard library/OS. Domain and HOST never acquire concrete filesystem dependency.

A10 State ownership

Destination is committed persistent state; caller owns submitted byte slice. Each invocation exclusively owns its temp path and open handle; no authoritative global state. Atomic counter, if used, is naming assistance only; create_new decides ownership.

A11 Mutation boundary

Only owning invocation writes/removes its temporary file. Destination changes only at successful rename. Never delete destination as replacement fallback.

A12 Transaction boundary

Create sibling exclusively -> write all -> sync file -> close -> rename over destination. Before successful rename, prior destination bytes remain unchanged. Error cleanup removes only owned temp, best effort; cannot promise cleanup if OS denies removal.

A13 External system boundary

Local filesystem behavior; Windows machine probe only. Network filesystems, adversarial directory mutation, symlink sandboxing, power loss and parent-directory fsync excluded.

A14 Forbidden dependencies

No new Manager/service/port/crate, per-target lock table, serialization change, CAS/version arbitration, background cleanup daemon, caller rewrite, public error variant, or remove-destination fallback.

BDD specification

Feature: Safe concurrent file persistence
  Background:
    Given an isolated writable local directory
  Rule: Each writer owns its preparation and commits a complete payload
    Scenario: Replace an existing file
      Given a file containing old bytes
      When new bytes are saved successfully
      Then the file contains exactly the new bytes
    Scenario: Concurrent saves commit complete payloads
      Given two saves are preparing different complete payloads for one file
      When both saves commit successfully in a controlled order
      Then the file contains exactly the last committed payload
    Scenario: Failure before commit preserves old bytes
      Given a file containing old bytes
      When saving fails before commit
      Then the file still contains exactly the old bytes
    Scenario: One failed save cannot damage another preparing save
      Given two saves are preparing independent payloads for one file
      When one save fails before commit and the other succeeds
      Then the file contains exactly the successful payload
    Scenario: Existing preparation collision is preserved
      Given an existing file conflicts with a preparation candidate
      When new bytes are saved successfully using another candidate
      Then the existing conflicting file remains unchanged
    Scenario: Empty payload is valid
      Given a file containing old bytes
      When an empty payload is saved successfully
      Then the file contains zero bytes
    Scenario: Replacement is denied
      Given replacement of the existing destination is denied
      When a save is attempted
      Then saving reports failure
      And the previous destination remains unchanged

Minimal skeleton after approval

write_atomic: keep public signature
private candidate naming: pid + AtomicU64 sequence; create_new is ownership authority; retry max128
private transaction helper: prepare / write_all / sync_all / close / rename
private test-only phase/failure callback: deterministic barriers and failure injection
error: close then best-effort cleanup owned temp; preserve original PortError
no public hook, global lock table, dependency, port, or manager
