Intent

Interactive Agent sessions hosted inside EluSlot must preserve project binding, permission prompts, cancellation, and evidence gates. Existing ProcessPort is a CLI output-drain port, not an interactive terminal or chat session boundary.

Earlier product directions remain: (1) EluSlot launches Agent CLI, (2) Agent connects via MCP, (3) Agent hosts EluSlot Web UI. This module adds (4) EluSlot hosts an interactive terminal or native Agent panel.

Mode comparison — EA-A vs EA-B

OptionWay & boundaryProcessPort fit
EA-A
Integrated terminal (PTY)		 Web terminal → proposed session/input boundary → PTY adapter → official Agent CLI or benign local interactive fixture first. Needs stdin, resize, interrupt, cleanup, project bind before spawn. DOES NOT FIT — current ProcessPort is non-interactive
EA-B
Native Agent panel		 EluSlot chat/session/approval/diff UI → application session boundary → Codex App Server / Claude Code programmatic adapters. Needs structured events, auth, never-auto-approve permissions, shared evidence gates. ORTHOGONAL — provider protocol, not ProcessPort stdin

Pros/cons (A): proves OS interactive capability early without Agent auth; needs new PTY seam; permission/diff UX stays CLI-native; Win ConPTY vs Unix PTY still open.

Pros/cons (B): product-owned approval/diff UX; larger first slice (protocol+auth+UI); does not prove PTY capability by itself.

Decision feed — PD-RUST-EMBEDDED-AGENT-DEC-01

Recommended: A — PTY feasibility first with one benign local interactive fixture (not live Agent auth). Verify input/resize/interrupt/close with project binding; session ends on panel close; no persistence/resume; no approval auto-accept. Only after capability proof choose one Agent provider; defer native chat/diff/permission framework.

  • A (recommended): throwaway PTY fixture feasibility packet; new PTY seam/dependency still needs explicit review before Skeleton.
