AR-GUARD Implementation-only enforcement + trusted host authority

recommendation

Route implementation through start_implementation; classify task intent from host-owned task data, not a caller-selectable generic flag. Resolve an approval reference on the host and bind task, project, fingerprint, architecture/BDD/skeleton revisions and behavioral RED identity before EXEC side effects. Keep genuine generic runs compatible.

alternatives

Explicit intent in every request is viable only if host verifies it; trusting a client approved boolean or caller label remains bypassable. Requiring Guard for every generic run changes existing behavior and is not recommended.

inside envelope

Read-only Guard decision review; preserve existing authorize_exec_start predicate and existing dependency direction.

requires approval

Authority ownership, trusted approval storage, intent classification, freshness/revocation policy and changed command DTO. Hashing client-supplied data alone is not authority proof.

skeleton

Host-owned ApprovalRecord resolver -> validated GuardPacketDto -> authorize_exec_start -> GuardExecPass -> start_run_ungated. ApprovalRecord stores task/project/fingerprint + approved revision IDs + RED evidence ID; lookup rejects missing, stale, revoked or mismatched records. UI submits reference, never self-authorizes.

blocked by

Owner must name trusted approval source and approval actor, decide storage/lifecycle and generic-run definition. No new repository/port is approved here.

test proposal

Counting ProcessPort/McpClientPort doubles: approved current implementation starts once; absent/stale/revoked/mismatched and generic-labelled implementation start zero. Genuine generic request preserves approved compatibility.

AR-PROC Explicit child exit plus independent stream completion

recommendation

Preserve try_wait child-exit meaning. Approve a ProcessPort observation extension exposing per-stream Open/EOF/Error and drained bytes; EXEC publishes terminal once child exit and both streams settled. For inherited pipes approve bounded drain timeout with explicit incomplete-output result. Cancel remains idempotent and must not silently claim complete output.

alternatives

Redefining try_wait to mean exit-and-EOF hides lifecycle change and can wait forever on inherited pipes. Blocking joins inside nonblocking polls violate the port promise.

inside envelope

Private reader bookkeeping and equivalent cleanup can be local only when current observable guarantees are unchanged. Current ProcessPort explicitly allows lossy UTF-8: split Unicode corruption is not proof of existing contract violation.

requires approval

Port shape, stream error model, drain timeout, terminal ordering, cancellation cleanup and any stronger Unicode contract.

skeleton

Adapter TrackedChild owns child, independent stream status/buffers and reader lifecycle. Process observation returns exit + stdout/stderr state. EXEC ActiveRun holds drain phase/deadline and emits one terminal after settled streams or declared incomplete timeout. Existing state owner remains EXEC; adapter owns OS resources.

blocked by

Owner chooses drain deadline, timeout/error projection, buffering limit/overflow policy and descendant-process cancellation scope. No numerical defaults are invented here.

test proposal

Controlled reader barrier after child exit; independent stderr EOF/error; cancel during drain; inherited pipe held open; deadline produces incomplete result; exactly one terminal and no post-terminal chunks. Exact Unicode split tests only after optional contract approval.

AR-FS Unique exclusively created sibling temp; complete-payload last-commit-wins

recommendation

Keep FileSystemPort signature. Approve each write owning a unique create_new sibling; prepare/write/sync then replace target. Concurrent successful commits use last-commit-wins, with final bytes one entire payload; precommit failure preserves prior target and cleanup touches only the failing writer temp. Do not promise crash durability or compare-and-swap.

alternatives

Per-destination lock adds lock identity/lifetime and cross-process scope questions. Unique temps alone do not define overwrite success, target replacement portability or crash durability.

inside envelope

Private unique-temp naming/exclusive creation can fit current adapter responsibility without changing public port. Port currently says prefer atomic replace when adapter can; it does not establish strong concurrency/durability contract.

requires approval

Formal concurrent-write success/failure semantics, supported overwrite platforms, cleanup/failure boundary and any durability guarantee. Test-only phase hooks should remain internal, not a new production port.

skeleton

write_atomic -> owned create_new temp sibling -> write_all -> sync_all -> platform-supported atomic replace -> owned-temp cleanup on failure. Internal test seam controls prepare/commit phases. FileSystemPort unchanged, no global manager or implicit lock service.

blocked by

Owner accepts last-commit-wins and excludes power-loss durability; platform replacement support must be verified before claiming portable atomic replacement.

test proposal

Barrier-controlled overlapping writes: independent temp ownership, final complete A/B, precommit old target preserved, failed writer cannot delete peer temp; Windows overwrite test and isolated cleanup test. No timing-only race proof.
